# Глава 24. WebAssembly Threads

Многопоточность в WebAssembly позволяет выполнять вычисления параллельно, используя несколько ядер процессора. Это даёт значительный прирост производительности для ресурсоёмких задач — обработки изображений, научных симуляций, машинного обучения и игровой физики. В этой главе мы разберём, как устроены потоки в WASM, как используется SharedArrayBuffer, какие атомарные операции доступны и какие меры безопасности необходимы.

## Многопоточность в WASM

В браузере многопоточность WebAssembly реализована на основе Web Workers. WASM-модуль выполняется в нескольких воркерах, которые разделяют общую линейную память через SharedArrayBuffer . Это позволяет потокам обращаться к одним и тем же данным без копирования.

### От одного потока к параллельному выполнению

Без многопоточности WASM-модуль выполняется в одном потоке (обычно главном или в одном воркере). Все вычисления выполняются последовательно, и даже мощный многоядерный процессор используется не полностью.

Многопоточность решает эту проблему. Модуль инстанцируется в нескольких воркерах с одной и той же разделяемой памятью. Каждый воркер выполняет свою часть работы параллельно. Результаты синхронизируются через атомарные операции.

### Практическая реализация: wasm-bindgen-rayon

В экосистеме Rust самый популярный способ добавить многопоточность — библиотека `wasm-bindgen-rayon`. Она связывает пул потоков Rayon (стандартный для Rust) с Web Workers и SharedArrayBuffer . Это позволяет использовать привычные параллельные итераторы (`par_iter()`) в WASM-коде, который выполняется в браузере.

```rust
use wasm_bindgen_rayon::init_thread_pool;
use rayon::prelude::*;

#[wasm_bindgen]
pub fn parallel_sum(data: &[i32]) -> i32 {
    // Инициализация пула потоков (вызывается один раз)
    // ...
    
    // Параллельная сумма с использованием всех ядер
    data.par_iter().sum()
}
```

В JavaScript требуется инициализация пула потоков с указанием количества воркеров:

```javascript
import init, { initThreadPool, parallel_sum } from './my_module.js';

await init();
await initThreadPool(navigator.hardwareConcurrency);
const result = parallel_sum(new Int32Array([1, 2, 3, 4, 5]));
```

### Webble: современный подход к многопоточности

В 2026 году появились более продвинутые решения, такие как **Webble** — асинхронный многопоточный рантайм для веба . Webble запускает Rust-футуры и замыкания в пуле Web Workers, разделяющих линейную память WASM-модуля, без блокировки главного потока или циклов событий воркеров .

Ключевые особенности Webble:

- **Две очереди выполнения**: локальные (pinned) задачи для работы с `!Send`-данными (`Rc`, `JsValue`) и задачи с возможностью кражи (stealable) для балансировки нагрузки .
- **Работа с main thread**: задачи могут отправлять работу на главный поток через `webble::on_main` для безопасного доступа к DOM и Web API .
- **Управление жизненным циклом**: рантайм имеет состояния `Uninit → Running → Shutdown`, может быть перезапущен без перезагрузки модуля .

```rust
use webble::{spawn, on_main};

// Задача в воркере
spawn(async {
    // Вычисление на фоновом потоке
    let result = expensive_computation().await;
    
    // Передача результата на главный поток для обновления DOM
    on_main(move || {
        update_dom(result);
    }).await;
});
```

## SharedArrayBuffer

SharedArrayBuffer — это фундамент многопоточности в WebAssembly. Это особый тип буфера, который может быть разделён между несколькими воркерами . Все воркеры читают и пишут в одну и ту же область памяти, что позволяет обмениваться данными без копирования.

В WebAssembly SharedArrayBuffer используется как разделяемая линейная память — память с атрибутом `shared: true` при создании `WebAssembly.Memory`:

```javascript
const memory = new WebAssembly.Memory({
    initial: 128,
    maximum: 256,
    shared: true,  // разделяемая память
});
```

Свойство `buffer` такого объекта — `SharedArrayBuffer`, а не обычный `ArrayBuffer` . Этот буфер может быть передан между воркерами через `postMessage`.

### Требования к компиляции

Для использования SharedArrayMemory WASM-модуль должен быть скомпилирован с определёнными target-фичами. В Rust это выглядит так:

```toml
[target.wasm32-unknown-unknown]
rustflags = [
    "-C", "target-feature=+atomics,+bulk-memory,+mutable-globals",
]
```

Эти фичи необходимы потому, что:
- **`atomics`** — поддержка атомарных операций для синхронизации потоков
- **`bulk-memory`** — эффективная инициализация разделяемой памяти
- **`mutable-globals`** — изменяемые глобальные переменные, используемые для управления состоянием потоков

Линковка модуля с разделяемой памятью возможна только если все объектные файлы скомпилированы с поддержкой этих фич. В противном случае линкер выдаёт ошибку .

## Атомарные операции

Атомарные операции — это механизм синхронизации доступа к разделяемой памяти из нескольких потоков. Без них чтение и запись данных могут привести к состояниям гонки, когда два потока одновременно изменяют одну ячейку памяти.

В WebAssembly атомарные операции доступны через инструкции `atomic.rmw.*` (read-modify-write):

```wat
;; Атомарное прибавление 1 к значению по адресу $addr
i32.atomic.rmw.add $addr

;; Атомарное сравнение с обменом
i32.atomic.rmw.cmpxchg $addr $expected $desired
```

В JavaScript доступ к атомарным операциям для SharedArrayBuffer осуществляется через глобальный объект `Atomics`:

```javascript
// Атомарное прибавление
const newValue = Atomics.add(sharedArray, index, 1);

// Атомарное сравнение с обменом
Atomics.compareExchange(sharedArray, index, expected, desired);

// Ожидание изменения значения (блокирующее)
Atomics.wait(sharedArray, index, expected);

// Уведомление ожидающих потоков
Atomics.notify(sharedArray, index, count);
```

### Синхронизация на уровне WASM

В WASM-коде синхронизация реализуется через комбинацию атомарных операций и инструкции `memory.atomic.notify` для пробуждения потоков, ожидающих изменения памяти .

Стандартные примитивы синхронизации (мьютексы, условные переменные) в многопоточных WASM-приложениях реализуются поверх этих инструкций. Например, в Rust для `wasm32-unknown-unknown` стандартный `std::sync::Mutex` не работает, но библиотеки вроде `wasm-bindgen-rayon` предоставляют свои реализации.

## Безопасность работы с памятью

SharedArrayBuffer даёт огромную гибкость, но создаёт риски безопасности. Без контроля доступа злонамеренный код мог бы использовать разделяемую память для атак по побочным каналам (например, Spectre), извлекая данные из других процессов.

### Кросс-оригинальная изоляция

Чтобы использовать SharedArrayBuffer, страница должна быть **кросс-оригинально изолирована** (cross-origin isolated) . Это достигается отправкой двух HTTP-заголовков при загрузке главного документа :

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

COOP запрещает совместное использование контекстов между разными источниками. COEP требует, чтобы все ресурсы (скрипты, изображения, WASM-модули) загружались с явными CORS-политиками (CORP-заголовками) .

Без этих заголовков `self.crossOriginIsolated === false`, SharedArrayBuffer недоступен, а инициализация пула потоков завершается ошибкой .

### Поддержка браузерами

Поддержка SharedArrayBuffer и WASM-потоков в основных браузерах (на 2026 год) :

| Браузер | Минимальная версия | Требования |
|---------|-------------------|------------|
| Chrome/Edge | 91+ | COOP + COEP заголовки |
| Firefox | 89+ | COOP + COEP заголовки |
| Safari | 16.4+ | COOP + COEP заголовки |

Все браузеры требуют кросс-оригинальной изоляции для работы с SharedArrayBuffer.

### Альтернативы COOP+COEP

Кросс-оригинальная изоляция сложна в развёртывании. Она блокирует OAuth- и платежные потоки, использующие popup-окна. Требует от всех сторонних встраиваемых ресурсов добавления CORP-заголовков .

Для решения этой проблемы предлагается **Document-Isolation-Policy** — новый API, упрощающий получение доступа к SharedArrayBuffer. Вместо двух сложных заголовков предлагается помещать документы, запрашивающие изоляцию, в отдельные процессы (Out-of-Process Iframes). Это изолирует их от потенциальных Spectre-атак без необходимости разрывать коммуникацию с popup-окнами и без изменений со стороны третьих сторон .

Этот подход уже тестируется в Chrome на таких приложениях, как Zoom, Gmail и Google Earth, которые активно используют SharedArrayBuffer для многопоточных вычислений .

### Проверка поддержки в рантайме

Перед использованием многопоточности рекомендуется проверять, поддерживает ли браузер SharedArrayBuffer:

```javascript
// Проверка поддержки потоков
if (crossOriginIsolated && typeof SharedArrayBuffer !== 'undefined') {
    // Поддержка есть, можно инициализировать пул потоков
    await initThreadPool(navigator.hardwareConcurrency);
} else {
    // Откат на однопоточный режим
    console.warn('SharedArrayBuffer not available, using single-threaded mode');
}
```

### Безопасное программирование

В многопоточном WASM-коде важно соблюдать несколько правил:

1. **Всегда синхронизируйте доступ к разделяемым данным**. Используйте атомарные операции или мьютексы.

2. **Избегайте гонок данных**. Два потока не должны одновременно читать и записывать одну ячейку памяти без синхронизации.

3. **Используйте hazard pointers для разделяемых объектов**. В Rust-экосистеме `js_sys::hazard` обеспечивает безопасность доступа к разделяемым объектам, гарантируя, что объекты не будут удалены, пока другие потоки обращаются к ним .

4. **Используйте инструменты статического анализа** для выявления потенциальных состояний гонки.

---

Многопоточность в WebAssembly — это мощный инструмент для высокопроизводительных вычислений в браузере. Она основана на SharedArrayBuffer, который требует кросс-оригинальной изоляции для безопасности. Атомарные операции обеспечивают синхронизацию доступа к разделяемым данным. Инструменты вроде `wasm-bindgen-rayon` и `webble` делают многопоточность доступной для Rust-разработчиков, а Document-Isolation-Policy упрощает развёртывание. Понимание этих механизмов позволяет эффективно использовать все ядра процессора в веб-приложениях.
