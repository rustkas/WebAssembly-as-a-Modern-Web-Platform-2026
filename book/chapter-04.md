# Глава 4. WASM vs Web Workers

Параллелизм в вебе — одна из ключевых тем, когда речь заходит о производительности. Для выполнения тяжёлых вычислений, не блокируя основной поток, в веб-платформе доступны две принципиально разные технологии: Web Workers и WebAssembly.

Web Workers — это механизм запуска JavaScript-кода в фоновых потоках . WebAssembly — это низкоуровневая виртуальная машина для высокопроизводительных вычислений. Они не конкурируют между собой — напротив, их совместное использование даёт максимальный эффект.

## Модели параллелизма в вебе

Исторически браузерный JavaScript выполнялся в одном потоке. Это означало, что все операции — вычисления, события, рендеринг DOM, анимации — выстраивались в одну очередь. Любая долгая операция блокировала отклик интерфейса. Пользователь видел «зависшую» страницу.

Web Workers решают эту проблему, позволяя запускать скрипты в фоновых потоках . Рабочий поток (worker) создаётся через конструктор `Worker()` и выполняет отдельный JavaScript-файл. Рабочий поток не имеет доступа к DOM и многим API, связанным с главным окном, но поддерживает стандартные возможности JavaScript: строки, массивы, объекты, JSON, а также fetch и XMLHttpRequest для сетевых запросов .

Обмен данными между основным потоком и рабочим происходит через систему сообщений. `postMessage()` отправляет данные, `onmessage` принимает их. Данные при этом копируются — структурированный алгоритм клонирования создаёт полную копию передаваемого объекта .

## Workers как изоляция потока ОС

Web Workers реализованы как потоки операционной системы. Браузер управляет пулом рабочих потоков, выделяя их по мере необходимости. Каждый Web Worker работает в отдельном контексте: для выделенных воркеров это `DedicatedWorkerGlobalScope`, для разделяемых — `SharedWorkerGlobalScope` .

У этой модели есть важное ограничение: **обмен данными между потоками происходит через копирование**. Для больших объёмов данных это создаёт накладные расходы — сериализация и десериализация занимают время и память.

Разделяемые воркеры (Shared Workers) позволяют нескольким страницам и вкладкам из одного источника обращаться к одному и тому же рабочему потоку . Это полезно для совместного использования состояния, но добавляет сложности с управлением портами.

Web Workers решают **организационную** проблему параллелизма: они дают возможность выполнять код параллельно. Но они не решают проблему **вычислительной эффективности** — внутри воркера по-прежнему выполняется JavaScript, со всеми его ограничениями для тяжёлых вычислений.

## WASM как изоляция вычислений

WebAssembly решает другую задачу. WASM-модуль выполняется в изолированной песочнице, управляемой виртуальной машиной браузера. Он не создаёт отдельный поток ОС — он выполняется в том же потоке, что вызвал его инстанцирование.

Изоляция WebAssembly — это изоляция **вычислений**. Модуль не имеет прямого доступа к операционной системе, файлам, сети и даже к памяти других модулей . Вся память ограничена линейной памятью модуля. Любая попытка выйти за границы вызывает ловушку (trap).

Эта модель обеспечивает безопасность при сохранении высокой производительности. WebAssembly не заменяет Web Workers — он делает вычисления быстрее в том потоке, где они выполняются.

## Совместное использование: WASM внутри Worker

Максимальная производительность достигается при комбинации обеих технологий: **WebAssembly выполняется внутри Web Worker**. Это даёт и параллелизм (отдельный поток), и вычислительную эффективность (WASM-код).

Направление ускорения здесь предсказуемо и хорошо задокументировано по отдельности каждым шагом: WASM обычно даёт кратный выигрыш относительно чистого JavaScript на вычислительно насыщенных циклах (порядок величины зависит от задачи и входных данных — см. главу 3), SIMD добавляет отдельный множитель за счёт векторизации (в задачах вроде рендеринга частиц или матричных вычислений типично 1.7–4.5×, по данным бенчмарков TensorFlow.js WASM-бэкенда), а распределение по Web Workers может давать почти линейное ускорение по числу ядер — если задача действительно параллелится без гонок за общими данными. Перемножение этих трёх множителей на конкретном демо со множеством кубов на сцене вполне может давать суммарное ускорение в районе 40–60× относительно однопоточного JS без SIMD — но у меня нет источника на конкретную цифру «240 000 кубов» с точными миллисекундами из таблицы, поэтому раздел стоит либо подкрепить ссылкой на реальный демо-проект, либо оставить как иллюстративную, а не измеренную оценку.

Веб-рендеринг на WebGPU — ещё один пример эффективной связки. В проекте `webgpu-worker-leptos` рендеринг через wgpu (Rust-обёртка над WebGPU) выполняется в Web Worker. Воркер получает управление через `transferControlToOffscreen`, владеет `OffscreenCanvas`, управляет циклом рендеринга через `requestAnimationFrame` и обрабатывает WebGPU-команды . Основной поток занимается только UI и событиями.

Microsoft реализовал поддержку .NET-кода, скомпилированного в WASM, в Web Workers. C#-код с атрибутом [JSExport] запускается в фоновом потоке, не блокируя UI. Основные рекомендации для такой архитектуры: минимизировать передачу данных, группировать операции в пакеты, следить за памятью и использовать персистентные воркеры из-за затрат на инициализацию WASM.

## SharedArrayBuffer и атомарные операции

Для эффективной работы нескольких потоков с общими данными WebAssembly использует **SharedArrayBuffer** и атомарные операции. SharedArrayBuffer позволяет нескольким воркерам читать и записывать одну и ту же область памяти без копирования. Это принципиально отличается от стандартного обмена через `postMessage`.

В WebAssembly `SharedArrayBuffer` используется как разделяемая линейная память — `shared`-память, которая в JavaScript представляется как SharedArrayBuffer . Это даёт возможность нескольким WASM-экземплярам в разных воркерах работать с одними и теми же данными.

Атомарные операции (`Atomics.add()`, `Atomics.compareExchange()` и др.) гарантируют, что чтение и запись разделяемых данных выполняются как неделимые операции. Это предотвращает состояния гонки.

SharedArrayBuffer стал доступен в браузерах благодаря многопоточности WebAssembly. Стандарт WebAssembly Threads использует Shared Memory для поддержки многопоточности на уровне инструкций . Непосредственно в рантайме .NET (dotnet/runtime) включение поддержки потоков в WASM-сборке активируется флагом `WasmEnableThreads`. Флаг `WasmShellEnableThreads` с похожим названием — это отдельный параметр UI-фреймворка Uno Platform, который использует свой bootstrapper поверх .NET WASM; по умолчанию там создаётся пул из нескольких Web Worker (размер настраивается через `WasmShellExtraEmccFlags`/`PTHREAD_POOL_SIZE`). Эти два флага легко перепутать, но они принадлежат разным слоям стека — если ваш проект не использует Uno Platform, актуален именно `WasmEnableThreads`.

### Ограничения безопасности

Использование SharedArrayBuffer требует особых мер безопасности. Высокоточные таймеры на базе SharedArrayBuffer могут использоваться для Spectre-атак — утечки данных через атаки по побочным каналам .

Чтобы защитить пользователей, SharedArrayBuffer доступен только на сайтах, которые включили **кросс-оригинальную изоляцию** (cross-origin isolation). Для этого требуются HTTP-заголовки :

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

COOP (Cross-Origin-Opener-Policy) запрещает совместное использование контекстов между разными источниками. COEP (Cross-Origin-Embedder-Policy) требует явного разрешения (CORP-заголовка) для загрузки ресурсов с других источников.

Эти заголовки сложны в развёртывании: COOP блокирует OAuth- и платежные потоки, использующие popup-окна. COEP требует от всех сторонних встраиваемых ресурсов добавлять CORP-заголовки .

Поэтому появился Document-Isolation-Policy — новый заголовок, упрощающий получение доступа к SharedArrayBuffer. Вместо двух сложных заголовков (COOP + COEP) достаточно одного Document-Isolation-Policy: isolate-and-require-corp: браузер помещает документ, запросивший изоляцию, в отдельный процесс (в терминологии Chromium — Out-of-Process Iframe), не разрывая при этом коммуникацию с cross-origin popup-окнами и не требуя от встраиваемых сторонних ресурсов добавлять CORP-заголовки. Функция уже не экспериментальная: она поставляется в Chrome и Edge начиная с версии 137. Среди сервисов, заинтересованных во внедрении Document-Isolation-Policy ради доступа к SharedArrayBuffer, разработчики Chromium называли Gmail, Google Meet и Zoom.

## Итог

Web Workers и WebAssembly решают разные задачи. Web Workers дают параллелизм — возможность выполнять код в фоновых потоках. WebAssembly даёт эффективность — возможность выполнять вычисления близко к нативной производительности. Совместное использование (WASM внутри Web Worker) даёт максимальный эффект: и параллелизм, и вычислительная эффективность.

SharedArrayBuffer и атомарные операции обеспечивают разделяемую память для нескольких потоков, но требуют настройки заголовков для безопасности. Альтернативы, такие как Document-Isolation-Policy, упрощают развёртывание и делают многопоточные вычисления доступными для широкого круга приложений.
