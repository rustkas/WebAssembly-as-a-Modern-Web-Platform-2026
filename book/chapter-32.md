# Глава 32. WASM + Web APIs

Одна из ключевых возможностей современного веба — доступ к физическим устройствам и сенсорам через Web APIs. WebAssembly-модули, однако, не имеют прямого доступа к этим API: WASM выполняется в изолированной песочнице, лишённой системных вызовов . Вместо этого взаимодействие с Web APIs всегда происходит через JavaScript-слой, который выступает в роли посредника . Этот подход обеспечивает безопасность, но требует осознанного проектирования интеропа для сохранения производительности.

## Геолокация, камера, Bluetooth

Современные браузеры предоставляют богатый набор API для доступа к функциям устройства. WebAssembly-код может использовать эти API только через JavaScript-прокси.

**Геолокация.** W3C Geolocation API позволяет определять местоположение пользователя. Для WASM-модулей доступ к этой информации возможен через импорт JavaScript-функций, которые вызывают `navigator.geolocation.getCurrentPosition()`.

**Камера и микрофон.** WebRTC API предоставляет доступ к медиа-устройствам. WASM-модуль может передать поток видео в обработчик на JavaScript, который затем отправит кадры в WASM для обработки.

**Bluetooth.** Web Bluetooth API позволяет подключаться к Bluetooth-устройствам. WebAssembly здесь выступает как вычислительный слой: JavaScript получает данные от устройства и передаёт их в WASM для анализа или трансформации.

**WebUSB, WebHID, WebMIDI, Web Serial.** Эти API предоставляют низкоуровневый доступ к периферийным устройствам . К 2026 году они поддерживаются в Chromium-браузерах . Однако их использование сопряжено с серьёзными рисками безопасности, о которых будет сказано ниже.

## Проксирование нативных API через JS-слой

Проксирование — основной паттерн взаимодействия WASM с Web APIs. Его суть в том, что WASM-модуль импортирует JavaScript-функции, которые выполняют вызовы к браузерным API.

### Базовый механизм

Спецификация WebAssembly JavaScript Interface определяет, как WASM-модули взаимодействуют с JavaScript-окружением . WASM-модуль объявляет импорты, а JavaScript предоставляет их при инстанцировании.

```javascript
// JavaScript-код проксирует доступ к Web API
const importObject = {
  api: {
    getGeolocation: () => {
      return new Promise((resolve) => {
        navigator.geolocation.getCurrentPosition(
          (pos) => resolve({ lat: pos.coords.latitude, lng: pos.coords.longitude })
        );
      });
    },
    getCameraStream: () => {
      return navigator.mediaDevices.getUserMedia({ video: true });
    }
  }
};

WebAssembly.instantiateStreaming(fetch('module.wasm'), importObject)
  .then(({ instance }) => instance.exports.main());
```

WASM-модуль импортирует эти функции и вызывает их как обычные WASM-функции. При передаче сложных объектов (например, медиа-потоков) используется `JsValue` или аналогичные механизмы.

### Прокси на уровне языка: пример MicroPython и Pyodide

В некоторых реализациях проксирование встроено на уровне языка. MicroPython для WebAssembly добавляет JavaScript-прокси (PyProxy) и JsProxy, позволяя Python-коду обращаться к DOM и Web API .

Pyodide использует аналогичный подход: объекты JavaScript обёртываются в `JsProxy`, а Python-объекты — в `PyProxy` .

```python
# Python-код в Pyodide, работающий с DOM через прокси
from js import document
element = document.getElementById("my-element")
element.innerHTML = "Hello from WebAssembly!"
```

### Оптимизация прокси-вызовов

Каждый переход через границу WASM↔JS создаёт накладные расходы . Поэтому для production-приложений рекомендуется:

1. **Группировать вызовы.** Вместо множества мелких вызовов передавать пакеты данных.
2. **Использовать zero-copy.** Передавать `SharedArrayBuffer` вместо копирования данных.
3. **Минимизировать синхронные вызовы.** Асинхронные операции (`fetch`, WebSocket) лучше выполнять на стороне JavaScript и передавать результат в WASM.

### Специфика для серверных WASM-приложений

В серверных сценариях (WASI, wasmCloud) проксирование API может быть встроено на уровне рантайма. Например, wasmCloud использует модель «хост-плагинов» — компоненты с определёнными WIT-интерфейсами, которые обеспечивают доступ к возможностям .

## Безопасный доступ к устройствам

Безопасность доступа к устройствам — одна из ключевых задач при использовании WASM + Web APIs. WebAssembly изначально проектировался с безопасностью как основным принципом: песочница, изоляция памяти и политика deny-by-default .

### Модель разрешений браузера

Доступ к большинству Web APIs требует явного разрешения пользователя . WASM-модули наследуют эту модель, поскольку все вызовы проходят через JavaScript:

- `camera` / `microphone` — доступ к камере и микрофону.
- `geolocation` — доступ к местоположению.
- `midi` — доступ к MIDI-устройствам (с опцией `sysex` для системных сообщений).
- `bluetooth` — доступ к Bluetooth-устройствам.

Проверка состояния разрешений выполняется через Permissions API:

```javascript
const result = await navigator.permissions.query({ name: "geolocation" });
if (result.state === "granted") {
  // Разрешение есть, можно вызывать API
} else if (result.state === "prompt") {
  // Нужно запросить разрешение
}
```

### Риски низкоуровневого доступа к устройствам

Новые Web API (WebUSB, WebHID, Web Serial, Web MIDI) предоставляют низкоуровневый доступ к периферийным устройствам . Исследования показывают, что это коренным образом меняет модель угроз :

- В прошлом устройства могли предполагать, что хост (ОС) является доверенным.
- Теперь хостом может быть вредоносный веб-сайт, который нельзя доверять.

Исследователи проанализировали 22 модели устройств от 15 вендоров и обнаружили, что многие позволяют перепрограммировать прошивку или переопределять макросы прямо из браузера . Атаки возможны на двух уровнях:

1. **Замена прошивки** — через WebUSB или Web MIDI злоумышленник может прошить устройство вредоносным кодом, который будет сохраняться даже после переподключения.

2. **Злоупотребление существующей функциональностью** — через WebHID злоумышленник может перепрограммировать макросы мыши или клавиатуры для ввода вредоносных команд.

Исследователи построили несколько полноценных эксплойтов, которые позволяют выполнить произвольный код на системе жертвы, полностью обходя песочницу браузера .

Исследователи предложили механизм, который производители устройств могут использовать для указания, что устройство «готово» к работе с браузерными API — опциональный механизм на самом устройстве, который браузер мог бы проверять .

### Практические рекомендации для WASM-приложений

1. **Запрашивайте минимально необходимые разрешения.** Не запрашивайте доступ к камере, если он не нужен.
2. **Используйте Permissions API для проверки перед вызовом.** Это позволяет корректно обрабатывать отказы.
3. **Не храните секреты в WASM-коде.** Даже в бинарном формате они могут быть извлечены.
4. **Для работы с периферией** в production-приложениях используйте подход «платформенной обвязки» (Platform Harness): доверенный компонент на JavaScript обрабатывает взаимодействие с устройством и передаёт данные в WASM.
5. **Следите за CVE.**марте 2026 года была зафиксирована и уже исправлена уязвимость CVE-2026-3542 — высокой степени опасности (CVSS 8.8) выход за границы памяти в реализации WebAssembly в Google Chrome, эксплуатируемый через специально сформированную HTML-страницу; исправлено в Chrome 145.0.7632.159. Обновляйте браузер своевременно — это не разовое напоминание, а стандартная практика: подобные уязвимости в движках WASM обнаруживаются регулярно, и именно оперативные обновления браузера, а не что-либо на стороне вашего приложения, закрывают этот класс риска.

---

WASM + Web APIs открывает широкие возможности для веб-приложений — от геолокации до управления периферийными устройствами. При этом безопасность остаётся ответственностью разработчика: использование Permissions API, минимальные запросы прав и осознание рисков при работе с низкоуровневыми API — необходимые условия для production-приложений.
