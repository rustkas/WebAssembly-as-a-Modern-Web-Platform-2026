# Глава 16. Go → WebAssembly

Go предлагает один из самых простых способов компиляции в WebAssembly. Стандартный тулчейн поддерживает WASM как целевую платформу с минимальной настройкой, а альтернативный компилятор TinyGo предоставляет ещё более лёгкие бинарные файлы. Однако Go в WebAssembly имеет фундаментальные ограничения, связанные с горутинами, сборщиком мусора и моделью памяти, которые делают его непригодным для некоторых сценариев использования в браузере.

## Проблема горутин и сборщика мусора

Компиляция Go в WebAssembly сталкивается с фундаментальными архитектурными несоответствиями между моделью выполнения Go и моделью WebAssembly.

### Горутины в однопоточной среде

WebAssembly в браузере выполняется в однопоточной среде — один поток выполнения, один стек. Go, напротив, изначально спроектирован для многопоточности с десятками тысяч горутин, которые планируются на несколько потоков ОС. При компиляции в WebAssembly возникает конфликт: как выполнять горутины, если настоящих потоков нет?

В `GOOS=js GOARCH=wasm` стандартный Go-рантайм отключает многопоточность. Все горутины выполняются на единственном потоке JavaScript, а операции блокировки (`time.Sleep`, `channel`, `select`) эмулируются через механизмы JavaScript — `setTimeout` и цикл событий. Это **кооперативная** многозадачность без настоящей параллельности.

Практические последствия:

```go
// ⚠️ Опасно: в WASM может заблокировать весь JS-поток
for i := 0; i < 1000; i++ {
    go func() {
        time.Sleep(10 * time.Millisecond) // эмулируется через setTimeout
        atomic.AddInt64(&counter, 1)
    }()
}
// Все 1000 горутин запускаются последовательно, без реального параллелизма
// Высокая задержка, возможна блокировка рендеринга
```

`time.Sleep` в WASM не приостанавливает горутину с освобождением потока — вместо этого она переводится в состояние ожидания, но другие горутины не могут выполняться в то же время. Это создаёт эффект «псевдопараллелизма» с высокой задержкой.

### Сборщик мусора и линейная память

Go использует сборщик мусора (GC) с поколенческой сборкой. В WebAssembly GC-объекты размещаются в линейной памяти — непрерывном блоке байтов, который не является управляемой кучей в смысле браузерного GC.

Это создаёт проблемы:

**Отсутствие OS-подсказок.** В нативной среде Go может получать информацию о доступной памяти от ОС. В WASM такие подсказки недоступны, поэтому GC работает в «слепую», что может приводить к частым и длительным паузам.

**Накладные расходы на GC.** Каждый вызов `fmt.Println` или `time.Now()` проходит через JavaScript-прокси (`syscall/js`), создавая накладные расходы 0.1–0.5 мс на вызов. Это накапливается в приложениях с интенсивным I/O.

Исследования показывают, что для Go WASM-приложений критическим является управление **побегами переменных в кучу**. Когда переменная «побегает» в кучу (например, при создании среза динамического размера), она становится частью GC-нагрузки:

```go
func processBatch(data []byte) []byte {
    buf := make([]byte, len(data)) // ❌ Переменная "побегает" в кучу
    copy(buf, data)
    return buf // buf — корневой объект для GC
}
```

В этом примере `make([]byte, len(data))` не может быть выделен на стеке, потому что размер известен только во время выполнения. GC вынужден отслеживать `buf`, увеличивая нагрузку.

## TinyGo vs стандартный компилятор

Существует два основных способа компиляции Go в WebAssembly: стандартный компилятор Go и TinyGo.

### Сравнение характеристик

| Характеристика | Стандартный Go | TinyGo |
|----------------|----------------|--------|
| Размер бинарного файла | 5–10 МБ | 100–500 КБ |
| Поддержка стандартной библиотеки | Полная | Частичная (reflect ограничен) |
| Время сборки | Быстрое | Дольше |
| Производительность выполнения | Переменная (смешанная) | Переменная (смешанная) |
| Поддержка WASI | Да (Go 1.21+) | Да |

**Стандартный Go** компилирует код в WASM с полной поддержкой стандартной библиотеки, включая `net/http`, `encoding/json` и `crypto`. Однако бинарный файл включает полный Go-рантайм с GC и планировщиком, что приводит к размеру 5–10 МБ даже для простых программ.

**TinyGo** — это альтернативный компилятор, ориентированный на ограниченные ресурсы. Он производит значительно меньшие бинарные файлы (100–500 КБ) за счёт удаления ненужных частей рантайма и использования более агрессивной линковки. Однако TinyGo имеет ограничения: неполная поддержка `reflect` и некоторых частей стандартной библиотеки.

### Сравнение производительности

Вопреки ожиданиям, TinyGo не всегда быстрее. Производительность выполнения зависит от характера нагрузки: на одних приложениях TinyGo быстрее, на других — стандартный Go.

Для сборки с TinyGo используется команда:
```bash
tinygo build -target=wasm -o main.wasm main.go
```

Для стандартного Go (WASI-цель):
```bash
GOARCH=wasm GOOS=wasip1 go build -o main.wasm main.go
```

Для браузера (с `syscall/js`):
```bash
GOOS=js GOARCH=wasm go build -o main.wasm main.go
```

### Оптимизация размера бинарных файлов

Для стандартного Go рекомендуется использовать флаги линковки для удаления отладочной информации:
```bash
GOOS=js GOARCH=wasm go build -ldflags="-s -w" -o main.wasm main.go
```

Альтернативные стратегии уменьшения размера:
- Минимизировать количество импортов (каждый импорт добавляет код)
- Ленивая загрузка тяжёлых функций через отложенную инициализацию
- Использовать сжатие через gzip/brotli при передаче по сети

## Когда Go подходит для WASM (CLI, сервер)

Go в WebAssembly наиболее эффективен за пределами браузера, где его ограничения (размер бинарника, отсутствие реальной многопоточности, неэффективный GC в линейной памяти) менее критичны.

### CLI и тулы

Go WASM-модули отлично подходят для CLI-инструментов, запускаемых через WASI. Пример: решение задачи N-ферзей, где бизнес-логика написана на Go и может быть скомпилирована как в нативный CLI, так и в WASM-модуль для веб-интерфейса.

Преимущества для CLI:
- **Переносимость**: один бинарник работает на всех платформах с WASM-рантаймом
- **Безопасность**: строгая изоляция через WASI
- **Простота**: Go-код компилируется без изменений

### Серверные и edge-приложения

Fastly Compute SDK и другие платформы поддерживают Go как язык для edge-вычислений. Go WASI-модули запускаются на Wasmtime и других рантаймах, обеспечивая низкий холодный старт и безопасную изоляцию.

Преимущества для сервера:
- **WASI-поддержка**: Go 1.21+ официально поддерживает WASI Preview 1 (`GOOS=wasip1`)
- **Меньший размер**: по сравнению с контейнерами, WASM-модули на Go компактнее
- **Предсказуемость**: отсутствие JIT-компиляции даёт стабильную производительность

### Передача строк через линейную память

В экосистеме Go/WASM существует проблема передачи строк между WASM-модулем и хостом. `syscall/js` позволяет напрямую читать DOM, но эта связка работает только в браузере и несовместима с WASI. TinyGo вообще не поддерживает `syscall/js` в некоторых конфигурациях.

Решение: передача строк через линейную память в виде байтовых массивов. Это универсальный подход, работающий и в браузере, и в WASI-средах. Данные сериализуются в массив байтов, записываются в WASM-память, а хост читает их оттуда.

## Ограничения Go в браузере

Браузер — самая сложная среда для Go WASM из-за архитектурных несоответствий и накладных расходов на JavaScript-мост.

### Отсутствие прямого доступа к DOM

**WebAssembly не имеет прямого доступа к DOM.** Это не ограничение Go, а фундаментальное свойство WASM. Взаимодействие с DOM всегда происходит через JavaScript, и Go делает это через `syscall/js`.

Механизм: `syscall/js` использует JavaScript-глюк-код (`wasm_exec.js`), который перехватывает вызовы Go и транслирует их в JS-вызовы. Каждое обращение к DOM проходит через этот мост:

```
Go-код → syscall/js → wasm_exec.js → JavaScript → DOM
```

Это создаёт накладные расходы: вызов `fmt.Println` может занимать 0.1–0.5 мс только из-за перехода через JS-мост.

### Размер и время загрузки

Даже минимальный Go WASM-модуль для браузера требует:
1. Бинарный файл WASM (5–10 МБ)
2. Файл `wasm_exec.js` (~20 КБ) для JS-интеропа

5–10 МБ — слишком много для веб-приложения, где критично время до интерактивности. Это делает Go непригодным для браузерных сценариев, требующих быстрой загрузки.

TinyGo решает проблему размера (100–500 КБ), но ценой ограниченной поддержки стандартной библиотеки и `reflect`. Для многих веб-приложений этого недостаточно.

### Ограниченная многопоточность

Как уже обсуждалось, в `GOOS=js GOARCH=wasm` нет реальной многопоточности. `GOMAXPROCS` принудительно устанавливается в 1. Это означает, что:

- Горноутины не могут выполняться параллельно на нескольких ядрах
- Блокирующие операции (каналы, мьютексы) могут приводить к зависанию интерфейса
- Нет поддержки `sync.WaitGroup` в привычном виде без риска дедлоков

Альтернатива: использовать `js.Promise` и эмулировать параллелизм через асинхронные JS-вызовы, но это требует ручного управления и теряет удобство Go-горутин.

### Практические рекомендации для браузера

1. **Используйте TinyGo** для уменьшения размера бинарного файла.
2. **Минимизируйте количество переходов через JS-мост**: группируйте операции на стороне Go.
3. **Избегайте интенсивного использования GC** в циклах: минимизируйте создание объектов в куче.
4. **Лениво загружайте тяжёлые модули**: не инициализируйте всё при старте.
5. **Используйте компрессию**: gzip/brotli для передачи `.wasm`-файлов.

---

Go в WebAssembly — мощный инструмент, но с чёткими границами применимости. За пределами браузера (CLI, сервер, edge) Go WASM предоставляет простоту разработки, переносимость и безопасность. В браузере Go сталкивается с фундаментальными ограничениями: размер бинарных файлов, неэффективный GC в линейной памяти, отсутствие реальной многопоточности и накладные расходы на JS-мост. Для браузерных приложений лучше подходят Rust или AssemblyScript. Для серверных и CLI-сценариев Go — отличный выбор.

В следующей главе мы рассмотрим AssemblyScript — TypeScript-подобный язык, спроектированный специально для WebAssembly и лишённый многих ограничений Go в браузере.
