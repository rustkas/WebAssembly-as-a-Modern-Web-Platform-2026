# Глава 21. Потоковая компиляция

Ключевое преимущество WebAssembly перед JavaScript в контексте веб-приложений — возможность начинать компиляцию до того, как загрузка файла завершится. Это свойство, называемое потоковой компиляцией (streaming compilation), кардинально меняет время до интерактивности (Time To Interactive, TTI) для больших приложений. Вместо того чтобы ждать полной загрузки `.wasm`-файла, браузер начинает компилировать код по мере поступления данных .

## Оптимизация времени до интерактивности (TTI)

Время до интерактивности — метрика, измеряющая, сколько времени проходит от начала загрузки страницы до момента, когда пользователь может начать с ней взаимодействовать. Для WebAssembly-приложений TTI складывается из трёх компонентов:

1. Время загрузки `.wasm`-файла по сети.
2. Время компиляции байт-кода в машинный код.
3. Время инстанцирования модуля.

Традиционный подход с `WebAssembly.instantiate()` требует завершения всех трёх этапов последовательно: сначала полная загрузка файла, затем компиляция, затем инстанцирование. Потоковая компиляция (через `instantiateStreaming` или `compileStreaming`) позволяет выполнять этапы 1 и 2 параллельно .

Для больших модулей это даёт существенный выигрыш, хотя точная величина сильно зависит от размера модуля, скорости сети и мощности процессора пользователя — `ruby+stdlib.wasm` (реальный, многомегабайтный пример из проекта ruby.wasm, где `compileStreaming` используется как рекомендуемый способ загрузки) хорошо иллюстрирует сам сценарий, но конкретную пару цифр «на 40 мс быстрее» и «сокращение TTI на 80%» лучше не приводить как универсальный факт без ссылки на конкретный замер с конкретной конфигурацией сети/устройства.

 Важный нюанс: потоковая компиляция даёт наибольший эффект, когда скорость компиляции сравнима со скоростью загрузки или превышает её. V8 действительно собирает внутренние метрики о времени компиляции и стриминга в формате `V8.Wasm...MilliSeconds`/`...MicroSeconds` (это подтверждённый паттерн именования V8-гистограмм для WASM) — но названия конкретных счётчиков стоит сверять по актуальному исходному коду V8 (`histograms.xml`) на момент публикации книги, а не приводить в тексте как стабильный, неизменный API: внутренние метрики V8 переименовываются и добавляются между релизами чаще, чем публичные API.

Есть и компромисс: в некоторых браузерных движках (например, JavaScriptCore на iOS) `compileStreaming` может не давать полного выигрыша, потому что движок откладывает принятие решений о компиляции до момента инстанцирования, когда становится известен тип памяти . Однако в 2026 году эта проблема в основном решена, и потоковая компиляция считается стандартом.

## WebAssembly.compileStreaming

Метод `WebAssembly.compileStreaming` компилирует WASM-модуль непосредственно из потока байтов, возвращаемого `Response`-объектом (например, результатом `fetch()`), но **не инстанцирует** его . Результат — `Promise`, который разрешается объектом `WebAssembly.Module`.

```javascript
// Компиляция модуля в потоке
const module = await WebAssembly.compileStreaming(
  fetch("https://example.com/module.wasm")
);

// Дополнительная работа с модулем (например, передача в воркер)
// ...

// Позднее инстанцирование
const instance = await WebAssembly.instantiate(module, importObject);
instance.exports.main();
```

Этот метод полезен в сценариях, где инстанцирование нужно отложить или выполнить в другом контексте:

- **Передача модуля между воркерами** — `WebAssembly.Module` поддерживает структурное клонирование и может быть передан через `postMessage()` .
- **Кэширование скомпилированного модуля** — сохранение модуля для повторного использования без повторной компиляции.
- **Предварительная компиляция в фоне** — модуль компилируется, пока выполняется другая работа.

Спецификация WebAssembly Web API чётко определяет требования к `Response` для `compileStreaming`:

- MIME-тип должен быть **точно** `application/wasm` (дополнительные параметры не допускаются) .
- Ответ должен быть CORS-same-origin .
- Статус ответа должен быть OK (2xx) .

Если эти требования не выполняются, `Promise` отклоняется с `TypeError`.

## Сравнение производительности

### Streaming vs Non-streaming

Базовое сравнение `compileStreaming` и `compile` на больших модулях показывает выигрыш порядка 40 мс . Однако реальный выигрыш зависит от соотношения скорости сети и скорости процессора:

| Сценарий | Streaming | Non-streaming | Преимущество |
|----------|-----------|---------------|--------------|
| Медленная сеть, быстрый CPU | Компиляция завершается раньше загрузки | Загрузка + компиляция последовательно | **Значительное** — TTI определяется скоростью сети |
| Быстрая сеть, медленный CPU | Компиляция завершается после загрузки | Загрузка + компиляция последовательно | **Минимальное** — TTI определяется скоростью CPU |
| Очень быстрая сеть, очень медленный CPU | Компиляция занимает основное время | То же самое | Почти нет выигрыша |

В Chrome для анализа этих соотношений существуют специальные гистограммы . Если компиляция завершается до загрузки (`V8.WasmStreamingUntilCompilationFinishedMilliSeconds`), потоковый подход сработал эффективно. Если загрузка завершается до компиляции, выигрыш от потоковости минимален.

### Кэширование скомпилированного кода

Дополнительный уровень оптимизации — кэширование скомпилированного модуля в браузере. Chrome измеряет время десериализации из кэша через `V8.WasmDeserializeModuleStreamingMicroSeconds` . При повторных загрузках одного и того же модуля десериализация из кэша может быть значительно быстрее, чем полноценная компиляция.

### JavaScript vs WebAssembly: парсинг и компиляция

Стоит отметить, что WebAssembly имеет фундаментальное преимущество перед JavaScript в скорости обработки кода. Браузеры используют «базовые компиляторы» (baseline compilers), которые парсят WebAssembly и генерируют машинный код так же быстро, как WASM-файл загружается по сети . JavaScript, напротив, требует более длительного парсинга и прогрева JIT . Это означает, что для больших приложений потоковая компиляция WebAssembly даёт не просто инкрементальное улучшение, а качественно иной уровень TTI.

### Ограничения и компромиссы

Существует важное ограничение для использования потоковой компиляции в некоторых сценариях. В спецификации ES-модулей этап `ModuleEvaluation` выполняется **синхронно** в одном «тике» . Это создаёт проблему: если WASM-модуль имеет секцию `start` (точку входа, выполняемую при инстанцировании), асинхронное инстанцирование через `instantiateStreaming` откладывает выполнение `start` в следующий «тик», что несовместимо с синхронной природой ES-модулей .

Решение, которое используется в бандлерах, — удаление секции `start` и экспорт соответствующей функции, которая вызывается синхронно после завершения асинхронного инстанцирования . Это позволяет сохранить совместимость с семантикой ES-модулей и одновременно использовать преимущества потоковой компиляции.

## Работа с Response и Fetch API

`compileStreaming` и `instantiateStreaming` принимают `Promise<Response>` — то есть можно передать непосредственно результат вызова `fetch()` .

```javascript
// Наиболее эффективный способ
const { instance } = await WebAssembly.instantiateStreaming(
  fetch("module.wasm"),
  importObject
);
```

Ключевое требование: сервер должен отдавать `.wasm`-файл с **правильным MIME-типом**. Для WebAssembly это `application/wasm` .

```nginx
# Пример конфигурации для nginx
location ~ \.wasm$ {
    default_type application/wasm;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

Если MIME-тип не соответствует, `instantiateStreaming` и `compileStreaming` отклоняют `Promise` с `TypeError` . В этом случае приходится использовать fallback на `instantiate` с ручным преобразованием `Response` в `ArrayBuffer`.

## Сравнительная таблица методов

| Метод | Компиляция | Инстанцирование | Потоковый | Когда использовать |
|-------|-----------|----------------|-----------|-------------------|
| `instantiateStreaming(fetch(url), imports)` | Да | Да | Да | Стандартный подход, минимальный TTI  |
| `compileStreaming(fetch(url))` | Да | Нет | Да | Когда инстанцирование нужно отложить или выполнить в другом контексте  |
| `instantiate(bytes, imports)` | Да | Да | Нет | Fallback для браузеров без поддержки streaming или при некорректном MIME-типе  |
| `compile(bytes)` | Да | Нет | Нет | Когда инстанцирование отложено и streaming недоступен |

Важное уточнение: `compileStreaming` — это не просто «компиляция без инстанцирования». Он использует тот же механизм потоковой обработки, что и `instantiateStreaming`, поэтому выигрыш в производительности сохраняется .

В 2026 году потоковая компиляция стала стандартом де-факто для загрузки WebAssembly-модулей в браузере. Она поддерживается во всех современных браузерных движках и является предпочтительным методом для production-приложений, где время до интерактивности критично.
