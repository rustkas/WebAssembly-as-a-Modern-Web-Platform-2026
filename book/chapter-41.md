# Глава 41. Кэширование

Кэширование — это ключевая стратегия для снижения времени запуска WebAssembly-приложений и экономии ресурсов как на стороне клиента, так и на сервере. В отличие от JavaScript-кода, который парсится и компилируется при каждом запуске, WASM-модули можно скомпилировать в машинный код один раз и переиспользовать результат. Однако эффективное кэширование требует понимания того, что именно кэшируется, где и как обеспечивается актуальность кэша.

## Кэширование скомпилированного кода

Самый дорогой этап при запуске WASM-приложения — это компиляция байт-кода в машинный код. Кэширование скомпилированного кода позволяет пропустить этот этап при повторных запусках.

### На уровне браузера: кэш V8

Современные браузеры кэшируют скомпилированный машинный код WebAssembly на диске пользователя . Механизм работает следующим образом:

1.  При первом запуске модуля (через `instantiateStreaming` или `compileStreaming`) браузер компилирует байт-код в машинный код.
2.  Если размер `.wasm`-файла превышает **128 КБ**, браузер сохраняет сгенерированный машинный код в кэш.
3.  При повторной загрузке модуля по тому же URL браузер загружает уже готовый машинный код, минуя этап компиляции. Этот процесс десериализации значительно быстрее и менее требователен к CPU.

**Ключевое условие**: кэширование работает **только** с потоковыми API (`instantiateStreaming` и `compileStreaming`), а файл должен отдаваться с правильным MIME-типом `application/wasm`.

### На уровне рантайма: кэш Wasmtime, Wasmer, wazero

Серверные рантаймы предоставляют более гибкие механизмы кэширования, которые можно настраивать под конкретные сценарии.

**Wasmtime** поддерживает инкрементальную компиляцию с кэшированием на уровне отдельных функций (через фичи `incremental-cache` + `cranelift` и типаж `CacheStore`). Ключ кэша формируется на основе внутреннего представления (IR) каждой функции, что позволяет переиспользовать скомпилированный код для функций, совпадающих между разными версиями модуля или между модулями, использующими одни и те же библиотеки, даже если остальное содержимое различается. Точный процент попаданий в кэш сильно зависит от того, насколько похожи структуры сравниваемых модулей — не стоит закладываться на конкретную цифру «~75%» как на универсальную характеристику механизма.


**Wasmer** использует трейт `ModuleCache`, который может быть реализован для разных стратегий хранения: in-memory, файловая система или распределённое кэширование . Комбинаторы вроде `FallbackCache` позволяют строить многоуровневые кэши: быстрый in-memory кэш с медленным файловым в качестве fallback .

**wazero** (рантайм на Go) поддерживает кэширование скомпилированных функций в файловой системе через `NewCompilationCacheWithDir` . Кэш привязан к конкретной версии рантайма и архитектуре, что предотвращает конфликты при обновлении .

### Кэширование системных библиотек в Emscripten

Emscripten использует собственную систему кэширования для предкомпилированных системных библиотек (libc, libc++, libcompiler_rt) . Библиотеки кэшируются в директории `~/.emscripten_cache` и могут иметь множество вариаций в зависимости от настроек компиляции: поддержка многопоточности, обработка исключений, уровень оптимизации . При обновлении версии Emscripten кэш автоматически инвалидируется .

## Cache API

В браузере для управления кэшированием WASM-модулей на стороне клиента используется **Cache API** — механизм, позволяющий программно сохранять и извлекать ответы HTTP-запросов.

### Service Worker как посредник

Service Worker перехватывает запросы к `.wasm`-файлам и обслуживает их из кэша при наличии . Это даёт несколько преимуществ:

1.  **Офлайн-доступ**: приложение может работать без сети.
2.  **Контроль над версиями**: Service Worker может проверять актуальность закэшированной версии.

Однако простое кэширование по URL создаёт проблему: если версия библиотеки изменилась, а Service Worker продолжает отдавать старую, возникает несовместимость между JavaScript-частью приложения и WASM-модулем .

### Стратегия верификации версий

Для решения этой проблемы используется стратегия с верификацией версий :

1.  Service Worker отправляет на сервер идентификатор версии закэшированного модуля.
2.  Сервер проверяет, является ли эта версия всё ещё валидной. Валидность может определяться по:
    - Таблице валидных/невалидных версий (ручное управление);
    - Временному порогу (например, версии старше недели считаются невалидными) ;
    - Динамически, с учётом пользовательских факторов (скорость сети, предпочтения) .

Такой подход позволяет использовать закэшированную версию, даже если она не является самой последней, до тех пор, пока она совместима с текущим кодом приложения .

### Edge Differ для минимизации обновлений

При обновлении больших бандлов часто меняется лишь небольшая часть файлов. Edge Differ — это компонент на сетевом ребре (edge), который сравнивает старую и новую версии бандла и возвращает клиенту **только изменившиеся файлы** . Это значительно сокращает объём передаваемых данных по сравнению с полной перезагрузкой всего бандла .

## Версионирование модулей

Версионирование — это основа управления кэшем. Без чёткой стратегии версионирования невозможно гарантировать, что клиент использует совместимую версию WASM-модуля.

### Хеширование содержимого (Content-based Hashing)

Самый надёжный способ идентификации версии модуля — хеширование его содержимого . При изменении любого байта в исходном коде меняется хеш, а следовательно, и идентификатор версии.

```rust
// Пример из astrid_openclaw: кэш инвалидируется при изменении хеша исходного кода
pub(crate) struct CacheMeta {
    source_hash: String,        // blake3 хеш исходного кода
    bridge_version: String,     // версия моста
    kernel_hash: String,        // хеш версии рантайма
    wasm_hash: String,          // хеш скомпилированного WASM
}
```

Кэш инвалидируется при изменении любого из этих параметров .

### Версионирование в URL

Для браузерного кэширования проще всего использовать версию в URL, например: `module-v2.wasm` или `module.js?v=2`. Это гарантирует, что при изменении версии браузер загрузит новый файл, а не возьмёт его из кэша по старому URL.

### Инвалидация кэша при изменении рантайма

В серверных рантаймах кэш привязан к версии самого рантайма . wazero создаёт поддиректорию `wazero-{version}-{arch}-{os}` внутри директории кэша . Это гарантирует, что при обновлении рантайма старый кэш не будет использоваться, предотвращая несовместимость. Wasmer рекомендует учитывать `Engine::deterministic_id()` при формировании ключа кэша .

### Требования к реализации кэша

Серверные рантаймы предъявляют следующие требования к реализации кэша :

- **Уникальность ключей**: ключ должен однозначно идентифицировать модуль.
- **Частота загрузок > частоты сохранений**: кэш читается чаще, чем пишется.
- **Атомарные записи**: предотвращение чтения частично записанных файлов .

---

Эффективное кэширование WebAssembly требует комплексного подхода: от правильной настройки браузерного кэша и использования Cache API до продуманной стратегии версионирования и инвалидации на уровне рантайма. Ключевые принципы: версионирование через хеширование, привязка кэша к версии рантайма, использование потоковых API для включения браузерного кэширования и атомарные операции при записи в кэш для предотвращения коррупции. Правильно реализованное кэширование может сократить время запуска WASM-приложений на порядки и значительно снизить нагрузку на серверы и сеть.
