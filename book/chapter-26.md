# Глава 26. Обработка исключений

Обработка исключений долгое время была слабым местом WebAssembly. В отличие от нативных языков, где исключения являются базовой конструкцией управления потоком, WebAssembly изначально не имел встроенной поддержки исключений. Это создавало проблемы для языков вроде C++ и Rust, которые полагаются на исключения для обработки ошибок, заставляя рантаймы и компиляторы прибегать к дорогим обходным путям .

К 2026 году ситуация кардинально изменилась. WebAssembly Exception Handling Proposal, принятая в октябре 2023 года, добавила в WASM встроенные инструкции для выбрасывания и перехвата исключений . Эта спецификация стала основой для обработки исключений во всех основных браузерах и WASM-рантаймах.

## Механизм Exception Handling в WASM

### Теги (Tags) и исключения

В WebAssembly исключения типизированы. Каждый тип исключения определяется через **тег** (`tag`) — специальную конструкцию, объявляющую сигнатуру исключения: какие параметры оно передаёт при выбрасывании .

```wat
;; Определение тега исключения с одним параметром i32
(tag $my_error (param i32))
```

Теги могут быть импортированы из JavaScript, экспортированы в JavaScript или определены внутри модуля . Каждый тег имеет атрибут, указывающий, что это тег для исключения (в будущем могут появиться другие типы тегов), и тип, определяемый индексом в секции типов . Сигнатура тега должна иметь пустой тип результата и может иметь любое количество параметров .

### Try_table и обработка исключений

Исключения обрабатываются с помощью инструкции `try_table`. В отличие от традиционных `try/catch` в языках высокого уровня, `try_table` — это структурный блок, который сочетает `try`, `catch` и `catch_all` в одной инструкции :

```wat
(try_table (catch $my_error $handler)
  ;; тело try
  (call $might_throw)
)
```

`try_table` поддерживает четыре типа `catch`-клауз :
- `catch tag label` — перехватывает исключение указанного тега и передаёт управление на `label`, помещая аргументы исключения на стек .
- `catch_ref tag label` — аналогично `catch`, но также помещает ссылку на исключение (`exnref`) на стек .
- `catch_all label` — перехватывает любое исключение .
- `catch_all_ref label` — перехватывает любое исключение и помещает `exnref` на стек .

Блок, на который передаётся управление (`handler` в примере), должен объявлять тип результата, соответствующий аргументам исключения .

Важно: `try_table` перехватывает только исключения, созданные инструкцией `throw`. **Ловушки (traps)** не могут быть перехвачены `try_table` . Это сделано намеренно: ловушки обычно невосстановимы локально, и перехват traps мог бы привести к непредсказуемому поведению . Также `try_table` не перехватывает JavaScript-исключения, возникающие из-за переполнения стека или нехватки памяти .

### Бросание и повторное бросание

Исключение создаётся инструкцией `throw` с указанием тега и аргументов :

```wat
(throw $my_error (i32.const 42))
```

Когда исключение брошено, выполнение ищет ближайший охватывающий `try_table`. Если такой найден, стек сбрасывается до состояния на момент входа в `try_table`, и проверяются `catch`-клаузы в порядке их появления. Если ни одна не совпадает, исключение пробрасывается дальше по стеку вызовов .

Исключение может быть повторно брошено с помощью `throw_ref`, который принимает `exnref` (ссылку на перехваченное исключение) . Если передан `null`, возникает ловушка .

### Два подхода к исключениям в C++

Для C++ (через Emscripten) доступны два подхода :

1. **JavaScript-основанный (Emscripten EH)** — используется флаг `-fexceptions`. Исключения обрабатываются через JavaScript-прокси, что имеет высокие накладные расходы даже когда исключения не выбрасываются, но работает на всех движках с поддержкой WASM .
2. **Нативный Wasm (Wasm EH)** — используется флаг `-fwasm-exceptions`. Исключения обрабатываются непосредственно в WASM с помощью встроенных инструкций (`try_table`, `throw`). Это даёт меньший размер кода и меньшие накладные расходы, но требует поддержки в браузере .

В Unity 2026 года аналогичный выбор доступен для C#-кода, скомпилированного через IL2CPP: можно использовать JS-прокси или нативный Wasm EH . В Unity появилась возможность **полностью удалить** код обработки исключений из скомпилированного WASM, если исключения отключены в настройках (Enable Exceptions = None) .

### Эволюция поддержки в Rust

В Rust поддержка исключений в WASM долгое время была сложной темой. Базовый WASM не поддерживает раскрутку стека, и стандартный `wasm32-unknown-unknown` использует `panic=abort` . Однако с развитием Exception Handling Proposal и поддержкой `panic=unwind` ситуация меняется .

Для WASI-целей с версии 2026 года стала доступна сборка с `-Cpanic=unwind` при использовании ночного Rust и `-Zbuild-std` :

```bash
RUSTFLAGS='-Cpanic=unwind' cargo +nightly run -Z build-std --target wasm32-wasip2
```

Ключевое изменение — в WASI-системе теперь используется `libunwind` из wasi-sdk, что позволяет Rust-коду интероперировать с C/C++-кодом при обработке исключений .

Rust-компилятор теперь проверяет, поддерживает ли целевая платформа раскрутку. Если целевая платформа не поддерживает раскрутку (например, WASM без включённой фичи `exception-handling`), код обработки исключений не генерируется или заменяется на `unreachable` и `abort` .

### Архитектура: exnref и интеграция с компонентами

Новая модель обработки исключений в WASM вводит тип `exnref` — ссылку на объект исключения . При перехвате через `catch_ref` или `catch_all_ref` ссылка помещается на стек, и её можно использовать для повторного бросания или для передачи в хост-среду .

Это особенно важно для **Component Model**. Согласно Canonical ABI, исключение, брошенное в одном компоненте, не должно пересекать границу компонента — оно должно превращаться в ловушку . В рантайме Wasmtime это реализовано через обёртку каждого адаптера в `try_table` с `catch_all`, которая вызывает ловушку .

## Паника в Rust и исключения в C++

### Rust: от panic=abort к panic=unwind

В Rust стандартным поведением для WASM-целей долгое время был `panic=abort`. Это означало, что любая паника в Rust-коде немедленно приводила к ловушке и завершению WASM-модуля .

С 2026 года стало возможным использовать `panic=unwind` для WASM при соблюдении следующих условий:
- Использование ночного Rust-компилятора
- Сборка стандартной библиотеки с `-Zbuild-std`
- Включение фичи `exception-handling` в целевом WASM-модуле (или использование WASI, где эта фича поддерживается через `libunwind`)

Это позволяет паникам в Rust раскручивать стек, выполнять деструкторы и восстанавливаться после паники без перезагрузки WASM-инстанса . Это критично для серверных сценариев (например, Cloudflare Workers с Rust), где требуется сохранить состояние приложения после ошибки.

В браузерном контексте паники в экспортированных Rust-функциях при включённом `panic=unwind` перехватываются `wasm-bindgen` и передаются в JavaScript как исключения `PanicError`.

### C++ через Emscripten

Emscripten предоставляет два подхода к исключениям, и каждый имеет свои особенности:

**JavaScript-основанный подход** (`-fexceptions`):
- Работает во всех движках
- Высокие накладные расходы даже без исключений — каждый `try`-блок добавляет переход на JS-слой 
- Поддерживает стек-трейсы в JS (через `getExceptionMessage` при включённых `ASSERTIONS`) 

**Нативный Wasm-подход** (`-fwasm-exceptions`):
- Меньший размер кода и лучшая производительность 
- Требует поддержки Exception Handling в браузере
- Имеет лучшую интеграцию с отладкой: при включённых `ASSERTIONS` неперехваченные исключения печатают стек-трейсы 

В Emscripten существуют хелперы для работы с исключениями из JavaScript:
- `getExceptionMessage(e)` возвращает `[type, message]` для исключений, наследуемых от `std::exception` 
- `decrementExceptionRefcount(e)` — освобождает память, связанную с исключением, если оно было перехвачено в JS и не переброшено обратно 

## Проброс ошибок в JavaScript

### WebAssembly.Exception и WebAssembly.Tag

В JavaScript исключения из WASM представлены объектами `WebAssembly.Exception` . Этот объект содержит:
- Метод `is(tag)` — проверяет, соответствует ли исключение указанному тегу
- Метод `getArg(tag, index)` — возвращает значение аргумента исключения по индексу
- Свойство `stack` — стек-трейс (если включён при создании) 

Для перехвата и инспекции исключения в JavaScript необходимо иметь доступ к соответствующему тегу :

```javascript
// Создание тега в JavaScript
const myErrorTag = new WebAssembly.Tag({ parameters: ["i32"] });

// Передача тега как импорта в WASM-модуль
const imports = { env: { my_error: myErrorTag } };

// Вызов экспортированной функции с try/catch
try {
  instance.exports.throwFunction();
} catch (e) {
  if (e instanceof WebAssembly.Exception && e.is(myErrorTag)) {
    const payload = e.getArg(myErrorTag, 0);
    console.log('Exception payload:', payload);
  }
}
```

Тег, созданный в JavaScript, **должен** быть передан в WASM-модуль как импорт. Нельзя создать тег в JavaScript и использовать его для инспекции исключения, брошенного модулем с другим тегом, даже если сигнатуры совпадают .

### Проброс исключений через асинхронные границы

При работе с асинхронным кодом (промисы, async/await) важно, чтобы исключения корректно пробрасывались через границу WASM↔JS. В экосистеме Extism (JS PDK) были исправления, предотвращающие панику (`wasm error: unreachable`) при некорректной обработке промисов в асинхронных контекстах . Исключения теперь преобразуются в читаемые JS-ошибки со стек-трейсами вместо паники .

## Практические стратегии

### Выбор режима для C++

| Сценарий | Рекомендуемый подход |
|----------|---------------------|
| Production-приложение с интенсивным использованием исключений | `-fwasm-exceptions` для лучшей производительности |
| Совместимость со старыми браузерами/движками | `-fexceptions` |
| Код, где исключения редки и размер бинарника критичен | `-fno-exceptions` (исключения отключены) |

### Rust: управление паниками

Для Rust-кода в браузере:
- По умолчанию `panic=abort` — паника = ловушка
- Для перехвата паник на границе Rust↔JS использовать `panic=unwind` (ночной Rust, `-Zbuild-std`)
- В production-приложениях устанавливать глобальный перехватчик паник для логирования ошибок

### Обработка на границе компонентов

При использовании Component Model учитывайте, что исключения **не пересекают** границы компонентов — они превращаются в ловушки . Это означает, что каждый компонент должен обрабатывать исключения внутри себя и возвращать ошибки через обычные типы возврата (например, `Result` в Rust), а не полагаться на проброс исключений через границу.

### Отладка и мониторинг

- Для нативных Wasm-исключений в Emscripten используйте `-sASSERTIONS` для получения стек-трейсов при неперехваченных исключениях 
- В JavaScript используйте `WebAssembly.Exception.prototype.stack` для получения стек-трейса (доступно при создании исключения с `traceStack: true`) 
- В Rust-WASM-приложениях используйте глобальный перехватчик паник для отправки ошибок в систему мониторинга

### Управление памятью при исключениях

При перехвате исключения в JavaScript и неперебросе его обратно в WASM необходимо освободить память, связанную с исключением, с помощью `decrementExceptionRefcount` . В противном случае возникает утечка памяти. В Emscripten для упрощения работы существует хелпер `getExceptionMessage`, который автоматически управляет счётчиком ссылок (при использовании `-sEXPORT_EXCEPTION_HANDLING_HELPERS` и `-sASSERTIONS`) .

### Практический паттерн: обработка паник в Rust с `wasm-bindgen`

```rust
use wasm_bindgen::prelude::*;
use std::panic;

// Установка перехватчика паник для логирования
pub fn setup_panic_hook() {
    panic::set_hook(Box::new(|info| {
        let message = info.payload().downcast_ref::<String>()
            .map(|s| s.as_str())
            .or_else(|| info.payload().downcast_ref::<&str>().copied())
            .unwrap_or("Unknown panic");

        // Отправка ошибки в JavaScript (например, через console.error)
        web_sys::console::error_1(&format!("Panic: {}", message).into());

        // Возможна отправка в систему мониторинга через JS-коллбэк
    }));
}
```

---

Обработка исключений в WebAssembly в 2026 году — это зрелый механизм, основанный на спецификации Exception Handling с тегами, `try_table` и `exnref`. Для C++ через Emscripten доступны два подхода: JavaScript-основанный и нативный Wasm. Для Rust стала возможна сборка с `panic=unwind` на WASI-целях, что открывает путь к восстановлению после паник в серверных сценариях. JavaScript может перехватывать WASM-исключения через `WebAssembly.Exception` и `WebAssembly.Tag`. В Component Model исключения не пересекают границы компонентов, превращаясь в ловушки. Понимание этих механизмов необходимо для создания надёжных WASM-приложений, корректно обрабатывающих ошибки на всех уровнях.
