# Глава 20. Инстанцирование

Инстанцирование — это заключительный этап жизненного цикла WebAssembly-модуля в браузере. На этом этапе скомпилированный код (представленный объектом `WebAssembly.Module`) связывается с конкретным окружением — памятью, импортированными функциями и глобальными переменными — и превращается в исполняемый инстанс. Именно через инстанс JavaScript-код получает доступ к экспортированным функциям и данным модуля.

## От байт-кода к инстансу

Процесс перехода от байт-кода к исполняемому инстансу состоит из трёх этапов, которые могут быть объединены в один вызов или разделены для гибкости .

**Этап 1: Получение байт-кода.** Исходный файл с расширением `.wasm` загружается из сети, из IndexedDB или генерируется непосредственно в JavaScript. Результат — `ArrayBuffer` или `Uint8Array`, содержащий бинарное представление модуля .

**Этап 2: Компиляция в Module.** Байт-код компилируется в объект `WebAssembly.Module`. На этом этапе браузер проверяет корректность байт-кода, преобразует его в машинный код и сохраняет в виде компактного, оптимизированного представления. Объект `Module` — **не имеет состояния**. Он не содержит памяти, глобальных переменных или данных. Это чисто код, готовый к исполнению в любом окружении, которое предоставит необходимые импорты .

**Этап 3: Инстанцирование.** Создаётся объект `WebAssembly.Instance` на основе `Module` и объекта импортов. Инстанс — **состоятельный**. Он связывает код с конкретной памятью (`WebAssembly.Memory`), таблицами функций (`WebAssembly.Table`) и импортированными JavaScript-функциями . Инстанс подобен замыканию (closure) в функциональных языках: он объединяет код с окружением. Инстансы не могут быть клонированы структурно (structured clone) — они привязаны к конкретному рантайму и не могут быть переданы между воркерами напрямую .

```javascript
// Полный процесс в трёх шагах
fetch('module.wasm')
  .then(response => response.arrayBuffer())          // Шаг 1: байт-код
  .then(bytes => WebAssembly.compile(bytes))         // Шаг 2: компиляция в Module
  .then(module => new WebAssembly.Instance(module, importObject)) // Шаг 3: инстанцирование
  .then(instance => instance.exports.main());
```

## Синхронное и асинхронное инстанцирование

Инстанцирование может быть выполнено синхронно или асинхронно. Выбор определяет, будет ли основной поток браузера заблокирован во время создания инстанса.

### Синхронное инстанцирование: `new WebAssembly.Instance()`

Конструктор `new WebAssembly.Instance(module, importObject)` создаёт инстанс синхронно . Это означает, что код блокирует выполнение JavaScript до тех пор, пока инстанцирование не будет завершено.

```javascript
// Синхронное инстанцирование
const module = await WebAssembly.compile(bytes); // предположим, модуль уже скомпилирован
const instance = new WebAssembly.Instance(module, importObject);
instance.exports.exported_func();
```

Официальная документация предупреждает: поскольку инстанцирование больших модулей может быть дорогостоящим, разработчикам следует использовать синхронный конструктор **только когда синхронное инстанцирование абсолютно необходимо**. Во всех остальных случаях следует использовать асинхронный метод `WebAssembly.instantiateStreaming()`.

 Синхронный конструктор может выбрасывать исключения:
 - `TypeError` — если параметры имеют некорректный тип или структуру;
 - `WebAssembly.CompileError`, `WebAssembly.LinkError` или `WebAssembly.RuntimeError` — в зависимости от причины сбоя;
 - `RangeError` — в некоторых браузерах, запрещающих синхронную компиляцию и инстанцирование WASM с большими буферами на главном потоке. Это ограничение появилось в Chrome как защита от блокировки UI при полной (не ленивой) компиляции больших модулей; исходно порог составлял 4 КБ, что на практике часто ломало библиотеки, использовавшие синхронный путь по умолчанию. Позже Chrome поднял планку на порядок — до величины, близкой к максимальному размеру одной WASM-функции по спецификации (~7.6 МБ) — обосновав это тем, что современный ленивый компилятор V8 больше не блокирует поток так же тяжело, как раньше. Проверяйте актуальный порог в целевых браузерах и в любом случае используйте воркер или асинхронный путь для по-настоящему больших модулей, а не полагайтесь на конкретное число байт как на стабильный контракт.

### Асинхронное инстанцирование: `WebAssembly.instantiate()` и `WebAssembly.instantiateStreaming()`

Асинхронные методы не блокируют основной поток. `WebAssembly.instantiate(bytes, importObject)` принимает байт-код, компилирует его и инстанцирует в одном асинхронном вызове. `WebAssembly.instantiateStreaming(fetch(url), importObject)` делает то же самое, но начинает компиляцию по мере поступления байтов из сети.

Асинхронные методы всегда предпочтительнее для production-приложений, потому что они не прерывают рендеринг и не «замораживают» пользовательский интерфейс .

Существует также двухшаговый асинхронный вариант: `WebAssembly.compile(bytes)` для компиляции и затем `new WebAssembly.Instance(module, importObject)` для синхронного инстанцирования уже скомпилированного модуля. Этот вариант полезен, когда необходимо создать несколько инстансов одного модуля — компиляция выполняется один раз асинхронно, а синхронные инстансы создаются по мере необходимости.

## Передача импортов

Модуль объявляет импорты в своей секции импортов — функции, памяти, таблицы или глобальные переменные, которые должны быть предоставлены окружением. При инстанцировании все импорты передаются через объект `importObject` .

Импорты используют двухуровневое пространство имён: имя модуля и имя поля внутри этого модуля . Это соглашение соответствует ES-модулям и упрощает интеграцию.

```wat
;; simple.wasm
(module
  (func $log (import "console" "log") (param i32))
  (func (export "print")
    i32.const 42
    call $log
  )
)
```

JavaScript-код должен предоставить объект с точно совпадающей структурой:

```javascript
const importObject = {
  console: {
    log: (arg) => console.log(arg)
  }
};

WebAssembly.instantiateStreaming(fetch('simple.wasm'), importObject)
  .then(({ instance }) => instance.exports.print()); // выведет 42
```

Каждый объявленный импорт модуля должен иметь соответствующее свойство в `importObject`. Если свойство отсутствует или имеет несовместимый тип, выбрасывается `WebAssembly.LinkError` .

### Типы импортов

| Тип импорта | Представление в JavaScript | Описание |
|-------------|---------------------------|----------|
| Функция | `function` | Любая JavaScript-функция. Может принимать и возвращать WASM-типы. |
| Память | `WebAssembly.Memory` | Объект памяти, предоставляющий линейную память для модуля. |
| Таблица | `WebAssembly.Table` | Объект таблицы, хранящий ссылки на функции для косвенных вызовов. |
| Глобальная | `WebAssembly.Global` | Глобальная переменная, доступная модулю. |

### Импорт и экспорт из ES-модулей

WebAssembly-модули могут быть импортированы как ES-модули, и в этом случае импорты и экспорты следуют семантике ES-модулей. При интеграции с ESM возникает важный вопрос: **сколько инстансов создаётся при импорте модуля из нескольких мест?** Спецификация `HostResolveImportedModule` определяет, что при импорте одного и того же модуля из разных мест возвращается один и тот же экземпляр модуля .

Это поведение аналогично JavaScript-модулям: один модуль, один инстанс, общее состояние. Если два независимых компонента импортируют один WASM-модуль, они используют **один и тот же инстанс** и, следовательно, **общее состояние** (например, общую линейную память) .

```javascript
// a.js
import { increment } from './counter.wasm';
increment();

// b.js
import { increment } from './counter.wasm';
increment();

// c.js — инстанцирует a.js и b.js
// counter.wasm будет инстанцирован один раз, и increment будет вызван дважды
// на одном и том же инстансе. Если counter.wasm хранит внутреннее состояние,
// оно будет общим для a.js и b.js.
```

Это поведение может быть неочевидным и приводить к неожиданным побочным эффектам, если модуль имеет внутреннее состояние. В текущей версии ESM-интеграции невозможно получить отдельный инстанс модуля при импорте, отличный от «глобального» инстанса модуля, если только модуль не экспортирует фабричную функцию, которая создаёт новые инстансы при вызове .

## Множественные инстансы одного модуля

**Один `WebAssembly.Module` может быть инстанцирован многократно**, создавая несколько независимых инстансов с собственным состоянием. Это фундаментальное свойство разделения компиляции и инстанцирования .

```javascript
// Один модуль — множество инстансов
const module = await WebAssembly.compile(bytes);

// Создание двух независимых инстансов
const instance1 = new WebAssembly.Instance(module, importObject1);
const instance2 = new WebAssembly.Instance(module, importObject2);

// instance1 и instance2 имеют разные состояния (память, глобальные переменные)
// даже если они используют один и тот же код.
```

Каждый инстанс имеет собственное окружение: собственную линейную память (если модуль не использует разделяемую память), собственные глобальные переменные и собственные импортированные функции. Изменение состояния одного инстанса не влияет на другой инстанс того же модуля (при условии, что они не используют shared memory).

Это свойство делает `Module` идеальным кандидатом для передачи между воркерами через `postMessage()` — объект `Module` поддерживает структурное клонирование и может быть эффективно передан без повторной компиляции . Инстансы, напротив, не поддерживают структурное клонирование .

### Практическое применение множественных инстансов

1. **Изоляция данных между пользователями.** В многопользовательском приложении каждый пользователь получает отдельный инстанс модуля с собственными данными.

2. **Песочницы для плагинов.** Каждый плагин запускается в собственном инстансе, что изолирует его память и состояние от других плагинов.

3. **Одновременное выполнение одного алгоритма с разными параметрами.** Модуль с алгоритмом может быть инстанцирован несколько раз с разными конфигурациями.

4. **Переиспользование скомпилированного кода в воркерах.** Модуль компилируется один раз на главном потоке и передаётся в несколько воркеров, где каждый создаёт свой инстанс.

### Предостережения при множественных инстансах

- **Разделяемая память (Shared Memory)** — если несколько инстансов используют одну и ту же память (через `WebAssembly.Memory` с флагом `shared: true`), они будут разделять состояние. Это намеренное поведение для многопоточных приложений, но требует явного управления синхронизацией.
- **Глобальные переменные в импортах** — если модуль импортирует глобальные переменные (например, `WebAssembly.Global`), изменения в одном инстансе могут быть видны в другом, если используется один и тот же объект `Global`. Обычно это нежелательно, поэтому для каждого инстанса следует создавать отдельный `WebAssembly.Global` или передавать его отдельно.

### Инстанцирование без `Module`

`WebAssembly.instantiate(bytes, importObject)` может принимать байт-код и возвращать объект `{ module, instance }` — это объединение компиляции и инстанцирования в одном вызове. В этом случае `module` не сохраняется, но если он не нужен для создания других инстансов, подход удобен для простых сценариев.

### Сравнение методов инстанцирования

| Метод | Синхронность | Этапы | Когда использовать |
|-------|-------------|-------|-------------------|
| `new WebAssembly.Instance(module, imports)` | Синхронный | Только инстанцирование (требует готового `Module`) | Несколько инстансов одного модуля; когда синхронность критична |
| `WebAssembly.instantiate(bytes, imports)` | Асинхронный | Компиляция + инстанцирование | Одноразовая загрузка модуля; предпочтительнее синхронного подхода |
| `WebAssembly.instantiateStreaming(fetch(), imports)` | Асинхронный | Стриминговая компиляция + инстанцирование | Стандартный способ в production — минимальное время до интерактивности |
| `WebAssembly.compile(bytes) + new Instance()` | Асинхронный (компиляция) + синхронный (инстанцирование) | Компиляция, затем инстанцирование | Когда модуль компилируется заранее (в воркере) или сохраняется в кэше |

Инстанцирование — это точка, где безликий байт-код становится живым, работающим приложением. Понимание различий между методами инстанцирования, правильная передача импортов и осознанное управление множественными инстансами — основа для создания эффективных и масштабируемых WebAssembly-приложений.
