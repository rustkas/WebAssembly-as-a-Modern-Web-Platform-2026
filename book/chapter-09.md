# Глава 9. Линейная память (Linear Memory)

Линейная память — это фундаментальная концепция WebAssembly. В отличие от языков высокого уровня с управляемой кучей и сборщиком мусора, WebAssembly использует низкоуровневую модель памяти, где данные хранятся в непрерывном массиве байтов, доступном для прямого чтения и записи . Эта модель даёт разработчику полный контроль над управлением памятью, что критически важно для производительности и предсказуемости, но требует ручного управления и понимания того, как устроена память на уровне байтов.

## Модель песочницы

Каждый WebAssembly-модуль выполняется в изолированной среде (песочнице), отделённой от хост-рантайма . Изоляция реализуется на нескольких уровнях:

**Изоляция линейной памяти.** Модуль имеет доступ только к своей собственной линейной памяти. Память модуля изолирована от внутренней памяти рантайма и от памяти других модулей . Любая попытка обратиться к адресу за пределами выделенной области памяти вызывает ловушку (trap) — немедленное прерывание выполнения .

**Отсутствие прямых системных вызовов.** Модуль не имеет прямого доступа к операционной системе — файловой системе, сети, аппаратному обеспечению . Доступ к системным ресурсам возможен только через явно импортированные функции, которые хост-рантайм предоставляет модулю. Это реализует принцип наименьших привилегий .

**Политика одного источника.** В браузере WebAssembly-модули следуют политике одного источника (same-origin policy), как и JavaScript-код. Кросс-оригинальная загрузка WASM-модулей требует CORS-заголовков, а для безопасной доставки через CDN используется подресурсная целостность .

Эта модель безопасности устраняет целые классы уязвимостей, характерных для C/C++-программ :

- **Переполнение буфера.** В WebAssembly переполнение буфера в линейной памяти не может затронуть локальные или глобальные переменные, которые хранятся в индексном пространстве (фиксированного размера, адресуются по индексу) .
- **Использование указателей.** Указатели на функции и переменные с фиксированной областью видимости заменены индексами, что превращает ошибки указателей в ошибки индексов, которые обнаруживаются на этапе валидации или вызывают ловушку .
- **Уязвимости управления потоком.** Структурированное управление потоком и защищённый стек вызовов делают невозможными атаки возвратно-ориентированного программирования (ROP) и внедрение кода .

## Работа с сырыми байтами

Линейная память — это непрерывный массив байтов . Доступ к памяти осуществляется через инструкции загрузки и сохранения, которые специфицируют тип данных и смещение .

В JavaScript линейная память представлена объектом `WebAssembly.Memory`. Свойство `buffer` возвращает `ArrayBuffer` (или `SharedArrayBuffer` для разделяемой памяти), который представляет собой байтовый буфер . Доступ к байтам буфера осуществляется через типизированные массивы JavaScript (`Uint8Array`, `Int32Array` и т.д.).

Доступ к линейной памяти из WASM-кода осуществляется через инструкции загрузки (`i32.load`, `i64.load`, `f32.load`, `f64.load`) и сохранения (`i32.store`, `i64.store` и т.д.). Каждая инструкция указывает смещение (offset) от базового адреса и тип данных. Базовый адрес берётся из стека:

```wat
;; Сохранить 32-битное целое число 42 по адресу 16
i32.const 42
i32.const 16
i32.store

;; Загрузить 32-битное целое число из ячейки по адресу 16
i32.const 16
i32.load
```

Все операции с линейной памятью проверяют границы. Если адрес плюс размер операнда выходит за пределы выделенной памяти, возникает ловушка .

## Аллокаторы внутри WASM (wee_alloc)

Поскольку WebAssembly не предоставляет встроенного управления кучей, разработчик должен реализовать аллокатор внутри линейной памяти. Для языков с управляемой памятью (Rust, Go) стандартная библиотека предоставляет аллокатор. Для других случаев существуют легковесные альтернативы, такие как `wee_alloc` .

**Как работает wee_alloc.** `wee_alloc` — это минималистичный аллокатор, спроектированный для WebAssembly. Его ключевая особенность — стратегия инициализации кучи. Вместо того чтобы размещать кучу в пределах начальной памяти модуля, `wee_alloc` считает всю начальную память недоступной и использует инструкцию `memory.grow` для выделения первой страницы кучи .

Например, если модуль начинается с 1 страницы памяти (64 КБ), `wee_alloc` не использует эту страницу для кучи. Вместо этого он расширяет память на ещё одну страницу и начинает кучу с адреса 65536 (первый байт второй страницы) . Это гарантирует, что стек и статические данные, размещённые в начальной памяти, не будут перезаписаны кучей.

**Ручное управление памятью.** В языках, не предоставляющих встроенный аллокатор, разработчик может реализовать собственные функции выделения и освобождения. Например, в Rust-библиотеках часто определяются функции `alloc` и `free`, экспортируемые из WASM-модуля :

```rust
#[no_mangle]
pub fn alloc(size: usize) -> *mut u8 {
    let mut buf = Vec::with_capacity(size);
    let ptr = buf.as_mut_ptr();
    std::mem::forget(buf);
    ptr
}
```

Эта функция выделяет буфер в линейной памяти и возвращает указатель на него. Позже этот указатель может быть использован для записи данных из JavaScript:

```javascript
const ptr = Module._alloc(length);
const chunk = Module.HEAPU8.subarray(ptr, ptr + length);
chunk.set(data);
Module._free(ptr); // освободить
```

## Страницы памяти (64KB) и рост памяти

Память в WebAssembly измеряется в **страницах**. Одна страница равна 64 КБ (65,536 байт) . Это значение фиксировано спецификацией и не может быть изменено. Размер 64 КБ выбран как эффективный компромисс между гранулярностью выделения и накладными расходами на управление памятью.

**Инициализация памяти.** При создании экземпляра `WebAssembly.Memory` разработчик указывает начальное (`initial`) и опциональное максимальное (`maximum`) количество страниц :

```javascript
const memory = new WebAssembly.Memory({
  initial: 1, // 1 страница = 64 КБ
  maximum: 10, // максимум 10 страниц = 640 КБ
});
```

Если максимальное количество страниц не указано, память может расти неограниченно (до лимитов, установленных рантаймом).

**Рост памяти.** Метод `grow(delta)` увеличивает количество страниц памяти на указанное значение `delta` :

```javascript
const bytesPerPage = 64 * 1024;
console.log(memory.buffer.byteLength / bytesPerPage); // "1"
console.log(memory.grow(1)); // "1" — возвращает прежний размер
console.log(memory.buffer.byteLength / bytesPerPage); // "2"
```

Ключевые особенности роста памяти :

- **Отделение буфера.** При каждом вызове `grow`, даже с `delta = 0`, существующий `ArrayBuffer` отделяется (`detach`). Его свойство `byteLength` становится равным нулю, и доступ к данным через старый буфер становится невозможным. После вызова `grow` свойство `buffer` возвращает новый `ArrayBuffer` с обновлённой длиной .
- **Проверка максимума.** Если текущий размер плюс `delta` превышает максимальный размер, указанный при создании памяти, выбрасывается исключение `RangeError` .
- **64-битная адресация.** Для памяти с адресным типом `"i64"` (Memory64) параметр `delta` и возвращаемое значение имеют тип `BigInt` .

## Shared Memory

Разделяемая память (`SharedArrayBuffer`) позволяет нескольким Web Workers и WASM-модулям обращаться к одной и той же области линейной памяти . Это основа для многопоточности в WebAssembly.

**Создание разделяемой памяти.** Для создания разделяемой памяти используется флаг `shared: true`:

```javascript
const memory = new WebAssembly.Memory({
  initial: 128,
  maximum: 256,
  shared: true,
});
```

В этом случае свойство `buffer` возвращает `SharedArrayBuffer`, а не `ArrayBuffer` . Разделяемая память может быть передана между воркерами через `postMessage` с использованием передачи владения .

**Использование из нескольких воркеров.** Для того чтобы несколько WASM-экземпляров использовали одну и ту же разделяемую память, необходимо передать экземпляр `WebAssembly.Memory` в каждый воркер :

```javascript
// Основной поток
const memory = new WebAssembly.Memory({
  initial: 128,
  maximum: 256,
  shared: true,
});

const response = await fetch('module.wasm');
const module = await response.arrayBuffer();
const instance = await WebAssembly.instantiate(module, {
  env: { memory },
});

// Передача памяти в воркер
const worker = new Worker('worker.js', { type: 'module' });
worker.postMessage({ memory, module });
```

```javascript
// Воркер (worker.js)
onmessage = async (event) => {
  const { memory, module } = event.data;
  const instance = await WebAssembly.instantiate(module, {
    env: { memory },
  });
  // Использование той же памяти, что и в основном потоке
};
```

**Ограничения безопасности.** Использование `SharedArrayBuffer` требует настройки кросс-оригинальной изоляции (cross-origin isolation) для защиты от Spectre-подобных атак . Браузеры требуют отправки HTTP-заголовков:

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

Без этих заголовков `SharedArrayBuffer` недоступен .

**Внутреннее устройство.** В V8 разделяемая память WASM и `SharedArrayBuffer` в JavaScript используют одни и те же базовые структуры — `JSSharedArrayBuffer` и `BackingStore` . Это обеспечивает эффективный обмен данными без копирования.

**Атомарные операции.** Для безопасной работы с разделяемой памятью из нескольких потоков WebAssembly поддерживает атомарные операции (`atomic.rmw.add`, `atomic.rmw.sub`, `atomic.compare_exchange` и т.д.) в сочетании с `SharedArrayBuffer`. Они гарантируют, что чтение и запись разделяемых данных выполняются как неделимые операции, предотвращая состояния гонки .

---

Линейная память — это не просто деталь реализации. Это архитектурная основа WebAssembly, обеспечивающая производительность, безопасность и детерминизм. Понимание того, как она работает — от страниц и роста до разделяемой памяти и аллокаторов — необходимо для эффективного использования WebAssembly в production-приложениях. В следующих главах мы рассмотрим, как линейная память взаимодействует с системой типов, как организованы импорты и экспорты, и как на этой основе строятся полноценные приложения.
