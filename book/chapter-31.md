# Глава 31. WASM + WebGPU

WebAssembly и WebGPU вместе создают среду, которая по возможностям приближается к нативным платформам. WebAssembly обеспечивает эффективное выполнение на CPU, WebGPU — высокопроизводительный доступ к GPU. Их связка позволяет веб-приложениям достигать производительности, ранее доступной только нативному ПО, особенно в области игр, 3D-визуализации и вычислений общего назначения.

## Управление буферами вершин

WebGPU использует буферы для хранения данных — вершин, индексов, униформ-переменных и произвольных данных для compute-шейдеров. Буфер создаётся через `device.createBuffer` с указанием размера и флагов использования (`GPUBufferUsage.VERTEX`, `COMPUTE`, `STORAGE` и др.).

### Загрузка данных в GPU-буферы

Современный подход к управлению буферами строится на стратегии предзагрузки. Все данные, необходимые для рендеринга — геометрия, текстуры, материалы — загружаются в GPU-буферы заранее, до начала рендеринга . При отрисовке кадра данные ссылаются по смещениям, что минимизирует количество операций записи в буферы во время выполнения.

Архитектура **awsm-renderer** демонстрирует эффективный подход к управлению буферами :

- **DynamicUniformBuffer** — для данных фиксированного размера (матрицы трансформаций, параметры материалов). Управление буфером оптимизировано за счёт предсказуемого размера данных.
- **DynamicStorageBuffer** — для гетерогенных данных переменного размера (вершинные атрибуты, индексы мешей). Используются продвинутые техники управления для эффективного использования памяти при сохранении простого API.

Обновления данных помечают буферы как "грязные" (dirty), и в начале следующего кадра все изменения загружаются в GPU одним большим memcpy на буфер. Это делает обновление данных много раз за кадр (например, для физической симуляции) очень эффективным, поскольку не требует отдельных вызовов записи для каждого изменения .

### Предзагрузка и пулы буферов

Для минимизации динамических аллокаций в критических путях рендеринга используется подход с пулами буферов. Буферы создаются заранее и переиспользуются между кадрами. Это особенно актуально для GPU-памяти, где динамическое выделение может вызывать непредсказуемые задержки .

Структура, реализующая пул буферов:
```javascript
class BufferPool {
    constructor(device, size, count) {
        this.buffers = Array(count).fill().map(() => 
            device.createBuffer({ 
                size, 
                usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_SRC 
            })
        );
        this.available = [...Array(count).keys()];
    }

    acquire() {
        const index = this.available.pop();
        return this.buffers[index];
    }

    release(buffer) {
        this.available.push(this.buffers.indexOf(buffer));
    }
}
```

При таком подходе WASM-модуль может записывать данные непосредственно в предварительно выделенные буферы, избегая накладных расходов на создание новых буферов в рантайме .

### Zero-copy через SharedArrayBuffer

Ключевая стратегия оптимизации взаимодействия WASM и WebGPU — устранение копирования данных между WASM-линейной памятью и GPU-буферами . SharedArrayBuffer позволяет WASM-модулю и WebGPU обращаться к одной и той же области памяти:

1. WASM-модуль записывает данные (вершины, текстуры, параметры) непосредственно в SharedArrayBuffer.
2. WebGPU создаёт GPUBuffer, ссылающийся на ту же память.
3. Данные передаются в GPU без промежуточного копирования через CPU .

В Rust-экосистеме это реализуется через `web-sys`-биндинги к WebGPU , где буферы создаются через `device.create_buffer_with_data` или `device.create_buffer` с последующей записью данных.

## Шейдеры из WASM

Шейдеры в WebGPU пишутся на языке WGSL (WebGPU Shading Language) — языке, специально спроектированном для безопасного GPU-программирования. В контексте WASM-приложений шейдеры могут быть:

- Встроены в WASM-модуль как строковые константы;
- Загружены отдельным файлом и переданы в WebGPU через обёртку;
- Сгенерированы динамически на основе конфигурации приложения.

### Управление шейдерами из WASM

В Rust-экосистеме шейдеры управляются через `web_sys::GpuShaderModule`, который создаётся из строки WGSL-кода. **awsm-renderer** использует шаблоны Askama для генерации шейдеров: это позволяет переиспользовать код и легко управлять кэшированием на основе различных переменных, доступных шаблону .

Процесс компиляции шейдера в браузере обычно включает:
1. Компиляцию WGSL-кода через `glslang` в SPIR-V;
2. Трансляцию SPIR-V в WGSL через `tint` .

Библиотека **torsh_core** предоставляет абстракции для WGSL-шейдеров, включая автоматическое вычисление размера ворк-групп для compute-шейдеров .

### Immediate Values в WGSL

Нововведение в WebGPU — поддержка immediate-значений (также известных как push-константы или root-константы). Это позволяет передавать небольшие объёмы часто меняющихся данных в шейдер без создания GPU-буферов и управления бинд-группами .

В WGSL-шейдере:
```wgsl
requires immediate_address_space;

var<immediate> color: vec4f;

@fragment fn fragmentMain() -> @location(0) vec4f {
    return color;
}
```

В JavaScript:
```javascript
myRenderPassEncoder.setImmediates(0, new Float32Array([255, 0, 0, 255]));
```

Для небольших данных (цвет объекта, ID трансформации) immediate-значения дают значительное снижение CPU-накладных расходов по сравнению с униформ-буферами .

### Модель шейдеров в игровых движках

Игровые движки на WASM + WebGPU используют сложную модель управления шейдерами. **Flax Engine** компилирует шейдеры в SPIR-V через `glslang`, а затем в WGSL через `tint` . Движок поддерживает динамическую генерацию шейдеров в зависимости от аппаратных возможностей: текстурные форматы проверяются через `GPUDevice::Instance->GetFormatFeatures()` .

## Игровые движки на WASM + WebGPU

К 2026 году несколько игровых движков и рендереров используют связку WASM + WebGPU для production-приложений.

### Flax Engine

Flax Engine поддерживает экспорт игр в браузер через WebAssembly и WebGPU . Ключевые технические решения:

- **WebGPU** для рендеринга;
- **Фиксированный SIMD** в WebAssembly для ускорения вычислений;
- **JavaScript Promise Integration (JSPI)** для вызова асинхронных WebGPU-API из синхронного WASM-кода.

Требования к браузерам на 2026 год:
- Chrome/Edge: v137+ (май 2025);
- Firefox: v147+ (январь 2026) с включённым флагом JSPI;
- Safari: только Technology Preview 238+ (февраль 2026) .

Flax может использовать Asyncify вместо JSPI для широкой совместимости ценой большего размера бинарного файла .

### Galfus Engine

Galfus Engine — движок на Rust с рендерингом через wgpu (WebGPU), спроектированный как host-agnostic . Архитектура строится на очереди команд, разделяющей логику хоста и GPU-рендеринг:

```
Host Layer (JS/TS, Lua, Python, etc.)
    │ Команды (MsgPack)   │ События (MsgPack)
    ▼
┌────────────────────────────────┐
│        Galfus Core (Rust)      │
│  • Resource Management         │
│  • GPU Rendering (WGPU)        │
│  • Input Processing            │
└──────────────┬─────────────────┘
               ▼
┌────────────────────────────────┐
│           GPU Layer            │
│  Vulkan / Metal / DirectX 12   │
└────────────────────────────────┘
```

Движок предоставляет C-ABI, что позволяет использовать его из Node.js (N-API), Lua, Python, а также в браузере через WASM . Коммуникация между хостом и движком осуществляется через MessagePack для быстрой бинарной сериализации.

### awsm-renderer

**awsm-renderer** — это Rust/WASM/WebGPU рендерер, специально спроектированный для веба . В отличие от большинства Rust-решений, использующих wgpu как абстракцию над WebGPU, awsm-renderer использует WebGPU API напрямую через `web-sys`-биндинги . Это даёт:

- Более прямое отображение на WebGPU API;
- Точный контроль над поведением в веб-контексте;
- Лучшее понимание того, что происходит под капотом.

awsm-renderer использует текстурные пулы — массивы текстур одинакового размера и формата, что упрощает биндинг и позволяет оставаться в рамках лимитов шейдеров. Пулы могут расти по мере необходимости .

### Тенденции: CUDA → WASM

Интересное направление — трансляция CUDA-кода в WASM с WebGPU-бекендом. Проект **cuda-wasm** позволяет переиспользовать существующие CUDA-ядра в браузере . Это значительно снижает барьер для переноса научных и ML-приложений в веб.

### Дополнительные экосистемные проекты

- **Flirp** — C# движок для браузера через Blazor WebAssembly и WebGPU, включающий сцену-граф, камеры, гиzmos, источники света .
- **Go wgpu** — унифицированная Go-обёртка над WebGPU с тремя бекендами: Pure Go (нативный через HAL), Rust FFI (wgpu-native), и браузерный (WASM). Поддерживает compute-шейдеры и полный WGSL-пайплайн .

---

Связка WebAssembly и WebGPU в 2026 году стала стандартом для высокопроизводительных веб-приложений. Движки вроде Flax и Galfus, рендереры вроде awsm-renderer, и инструменты вроде cuda-wasm показывают, что игры, 3D-визуализация и ML-вычисления в браузере достигли уровня, ранее доступного только нативному ПО. Ключевые техники — предзагрузка данных в буферы, zero-copy через SharedArrayBuffer, immediate-значения для часто меняющихся данных — позволяют достичь производительности, приближающейся к нативной, при сохранении безопасности веб-платформы.
