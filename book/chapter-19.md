# Глава 19. Загрузка WASM модулей

Загрузка и выполнение WebAssembly-модуля в браузере — это многоэтапный процесс, включающий получение байт-кода из сети, его компиляцию в машинный код и инстанцирование — создание исполняемого экземпляра модуля с его состоянием . JavaScript API предоставляет несколько методов для этих операций, различающихся по эффективности и времени выполнения.

## WebAssembly.instantiateStreaming

`WebAssembly.instantiateStreaming()` — самый быстрый и эффективный способ загрузки WASM-модуля в современном браузере. Этот метод принимает в качестве первого аргумента объект `Response` (например, результат вызова `fetch()`) и выполняет компиляцию и инстанцирование модуля непосредственно из потока байтов, поступающих по сети .

```javascript
WebAssembly.instantiateStreaming(fetch("module.wasm"), importObject)
  .then(results => {
    // Использование экспортированных функций
    results.instance.exports.main();
  });
```

Ключевое преимущество `instantiateStreaming` — в том, что он устраняет промежуточный шаг создания `ArrayBuffer` . Вместо того чтобы дожидаться полной загрузки файла, браузер начинает компилировать WASM-код по мере поступления данных. В Firefox 58 эта технология была впервые представлена как **потоковая компиляция** (streaming compilation), позволяющая коду начинать выполняться быстрее .

Технически `instantiateStreaming` работает так: как только браузер получает достаточно байтов для валидации и компиляции, он запускает эти процессы параллельно с загрузкой остальных данных. Компиляция и декодирование могут быть разделены на несколько потоков, что делает базовую компиляцию быстрее .

### Поддержка браузеров

В 2026 году `WebAssembly.instantiateStreaming` поддерживается во всех современных браузерах. Для отказоустойчивости рекомендуется использовать проверку:

```javascript
if (typeof WebAssembly.instantiateStreaming === "function") {
  WebAssembly.instantiateStreaming(fetch("module.wasm"), imports)
    .then(/* ... */);
} else {
  // Fallback на WebAssembly.instantiate
}
```

## WebAssembly.instantiate

`WebAssembly.instantiate()` — более старая, но всё ещё широко используемая функция. Она принимает байт-код WASM-модуля в виде `ArrayBuffer` или `Uint8Array` и возвращает Promise, который разрешается объектом с полями `module` и `instance` .

```javascript
fetch("module.wasm")
  .then(response => response.arrayBuffer())
  .then(bytes => WebAssembly.instantiate(bytes, importObject))
  .then(results => {
    // results.module — скомпилированный модуль
    // results.instance — инстанс для выполнения
    results.instance.exports.main();
  });
```

Существует две перегрузки `WebAssembly.instantiate()` :

1. `instantiate(bytes, importObject)` — принимает байт-код, компилирует и инстанцирует его. Возвращает Promise с объектом `{ module, instance }`.

2. `instantiate(module, importObject)` — принимает уже скомпилированный `WebAssembly.Module` и создаёт инстанс. Возвращает Promise, который разрешается непосредственно инстансом.

Вторая перегрузка полезна, когда модуль уже скомпилирован и сохранён (например, в кэше) — можно создать несколько инстансов одного модуля без повторной компиляции.

Исторически `WebAssembly.instantiate` и цепочка `WebAssembly.compile().then(new WebAssembly.Instance())` имели тонкие семантические различия; в современных реализациях они максимально унифицированы .

## WebAssembly.compile

`WebAssembly.compile()` — функция, которая только компилирует WASM-байт-код в `WebAssembly.Module`, не создавая инстанс . Это полезно в сценариях, где инстанцирование нужно отложить или выполнить несколько раз:

```javascript
// Компиляция модуля
fetch("module.wasm")
  .then(response => response.arrayBuffer())
  .then(bytes => WebAssembly.compile(bytes))
  .then(module => {
    // Сохранение модуля для будущего использования
    cachedModule = module;
  });

// Позже — инстанцирование того же модуля
const instance = new WebAssembly.Instance(cachedModule, importObject);
```

Другие варианты использования:
- Предварительная компиляция модуля в фоновом потоке (Web Worker);
- Кэширование скомпилированного модуля в IndexedDB;
- Передача модуля между воркерами через `postMessage()` .

### compileStreaming

Аналогично `instantiateStreaming`, существует метод `WebAssembly.compileStreaming()`, который компилирует модуль из потока байтов, но не инстанцирует его :

```javascript
WebAssembly.compileStreaming(fetch("module.wasm"))
  .then(module => {
    // Модуль скомпилирован, можно сохранить или инстанцировать
  });
```

Этот метод эффективнее `compile()`, потому что работает непосредственно со stream-ответом и начинает компиляцию до завершения загрузки.

## Стратегии загрузки

Выбор метода загрузки зависит от конкретного сценария использования и требований к производительности.

### Streaming vs Non-streaming

`instantiateStreaming` и `compileStreaming` всегда предпочтительнее, если браузер поддерживает их. Причина — **сокращение времени до интерактивности** (Time To Interactive, TTI) . Компиляция начинается до завершения загрузки, что особенно важно для больших модулей.

### Кэширование скомпилированных модулей

В production-сценариях критически важно избегать повторной компиляции. Chrome/V8 и Firefox реализуют это на уровне движка: если WASM-модуль загружается через `instantiateStreaming`/`compileStreaming` из `Response`, привязанного к конкретному URL, движок связывает скомпилированный машинный код с этим URL во внутреннем кеше (v8 использует "alt-data" поверх обычного HTTP-кеша ресурсов) — при повторном запросе того же URL с тем же содержимым компиляция пропускается полностью .

 Важный нюанс: это кеширование машинного кода работает именно через `Response`-объект, полученный из реального сетевого запроса (или из Cache API) — а не через ручную компиляцию из `ArrayBuffer`. Если вы вручную извлекаете байты и вызываете `WebAssembly.compile(bytes)`, вы каждый раз запускаете компиляцию заново, даже если сами байты были взяты из кеша — Cache API кеширует только сетевую передачу, а не результат компиляции. Правильный паттерн — передавать закешированный `Response` напрямую в `instantiateStreaming`, позволяя внутреннему кешу движка (а не вашему коду) решать, нужна ли перекомпиляция:

 ```javascript
 async function loadAndCacheModule(url, imports) {
   const cache = await caches.open('wasm-cache-v1');
   let response = await cache.match(url);

   if (!response) {
     response = await fetch(url);
     // Кешируем сам Response, а не байты отдельно —
     // именно это даёт движку "зацепку" за URL для кеша машинного кода
     await cache.put(url, response.clone());
   }

   // Передаём Response напрямую в instantiateStreaming.
   // Если движок уже видел этот URL/содержимое раньше — компиляция пропускается.
   const { instance } = await WebAssembly.instantiateStreaming(response, imports);
   return instance;
 }
 ```

 Версионируйте ключи кеша (например, включайте хеш содержимого в URL или в имя кеша) — при деплое новой версии модуля со старым URL пользователи будут получать устаревший код с закешированным машинным кодом.


Альтернативно, можно использовать `WebAssembly.Module` в качестве структуры данных для передачи между воркерами через `postMessage()` .

### Ленивая загрузка (Lazy Loading)

Для больших приложений рекомендуется **ленивая загрузка** — модуль загружается и компилируется только когда он действительно нужен. Например, модуль обработки изображений загружается только когда пользователь открывает редактор.

В сочетании с `instantiateStreaming` ленивая загрузка даёт минимальное время старта при первом обращении к функциональности.

### Оптимизация размера и транспорт

Бинарный формат WASM компактен, но его размер всё ещё влияет на скорость загрузки. Для production-сред:

1. **Сжатие** — передача `.wasm` файлов с gzip или brotli (браузеры поддерживают автоматическую распаковку);
2. **Минимизация размера модуля** — использование `wasm-opt` для удаления мёртвого кода;
3. **Разделение кода** — декомпозиция монолитных модулей на несколько smaller, которые загружаются по требованию.

### Выбор стратегии в зависимости от сценария

| Сценарий | Рекомендуемая стратегия |
|----------|------------------------|
| Загрузка модуля, который используется сразу при старте приложения | `instantiateStreaming` |
| Кэширование модуля для повторного использования в нескольких инстансах | `compileStreaming` + `new WebAssembly.Instance()` |
| Большие модули, которые не нужны сразу | Ленивая загрузка + `instantiateStreaming` |
| Требуется многократное инстанцирование одного модуля | `compile` + множественные `new WebAssembly.Instance()` |
| Совместимость с браузерами, не поддерживающими streaming | `fetch` + `response.arrayBuffer()` + `instantiate` |

Загрузка WASM модулей — это не просто вызов одной функции. Это комплексный процесс, который включает выбор метода компиляции, стратегию кэширования и оптимизацию сетевого транспорта. Современные браузеры дают разработчику инструменты для достижения минимального времени загрузки и максимальной производительности; задача разработчика — правильно применить эти инструменты в контексте своего приложения.
