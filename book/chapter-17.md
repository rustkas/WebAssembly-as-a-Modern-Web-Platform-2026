# Глава 17. AssemblyScript

AssemblyScript — это язык, который компилирует вариант TypeScript в WebAssembly . Он не является просто «TypeScript для WASM» — это самостоятельный язык со своим синтаксисом, который выглядит как TypeScript, но имеет совершенно иную семантику, адаптированную для статической компиляции . AssemblyScript создан специально для WebAssembly  и предоставляет разработчикам контроль на уровне, близком к «сырому» WASM, но с синтаксисом, знакомым веб-разработчикам .

## TypeScript-подобный синтаксис для WASM

AssemblyScript спроектирован так, чтобы быть максимально похожим на TypeScript. Это позволяет разработчикам, знакомым с экосистемой JavaScript/TypeScript, начать писать WebAssembly-модули без изучения нового языка .

Базовый пример на AssemblyScript выглядит так :

```typescript
export function fib(n: i32): i32 {
  var a = 0, b = 1
  if (n > 0) {
    while (--n) {
      let t = a + b
      a = b
      b = t
    }
    return b
  }
  return a
}
```

Компиляция в WASM выполняется одной командой:
```bash
asc fib.ts --outFile fib.wasm --optimize
```

### Два уровня работы: низкоуровневый и высокоуровневый

AssemblyScript предоставляет разработчику два подхода к написанию кода, которые можно смешивать :

**Низкоуровневый подход** — это работа непосредственно с сырыми инструкциями WebAssembly через встроенные функции. Например, доступ к линейной памяти через `load` и `store` компилируется напрямую в WASM-инструкции:

```typescript
store<i32>(ptr, load<i32>(ptr) + load<i32>(ptr, 4), 8)
```

Этот код эквивалентен следующему C-коду :
```c
*(ptr + 2) = *ptr + *(ptr + 1)
```

Большинство WASM-инструкций доступны в виде встроенных функций :
```typescript
i32.ctz(...)             // ctz<i32>(...)
f64.reinterpret_i64(...) // reinterpret<f64>(...)
i64.load32_u(...)        // <i64>load<u32>(...)
```

**Высокоуровневый подход** использует стандартную библиотеку, знакомую JavaScript-разработчикам: `Math`, `Array<T>`, `String`, `Map<K,V>`, типизированные массивы и другие . Тот же доступ к памяти через высокоуровневый API выглядит так:

```typescript
var view = new Int32Array(12)
view[2] = view[0] + view[1]
```

Этот подход использует управляемую стандартную библиотеку, в то время как низкоуровневый подход даёт максимальный контроль .

## Ограничения и отличия от TypeScript

AssemblyScript не является надмножеством TypeScript. Это **вариант** TypeScript — часть является подмножеством, часть — расширением, что делает его технически «вариантом» . Существует несколько фундаментальных ограничений, которые делают невозможным прямой перенос существующего TypeScript-кода.

### Статическая компиляция вместо JIT

TypeScript транслируется в JavaScript, который затем выполняется через JIT-компиляцию. AssemblyScript компилируется статически, **напрямую** в WebAssembly-байткод .

Это означает, что динамические возможности JavaScript, которые TypeScript описывает через свою систему типов, не могут быть поддержаны в AssemblyScript . Как сказано в официальной документации: «маловероятно, что AssemblyScript когда-либо будет поддерживать весь TypeScript» .

### Отсутствие `any` и `undefined`

В AssemblyScript нет типа `any` и нет `undefined` . Это требует переписывания кода:

```typescript
// ❌ Так нельзя
function foo(a?) {
  var b = a + 1
  return b
}

// ✅ Так нужно
function foo(a: i32 = 0): i32 {
  var b = a + 1
  return b
}
```

### Отсутствие объединений типов

На момент написания книги в AssemblyScript нет объединений типов (union types). Похожего эффекта можно достичь через дженерики :

```typescript
// ❌ Так нельзя
function foo(a: i32 | string): void { }

// ✅ Так можно
function foo<T>(a: T): void { }
```

### Типизированные объекты вместо динамических

Объекты должны быть явно типизированы через классы или `Map` :

```typescript
// ❌ Так нельзя
var a = {}
a.prop = "hello world"

// ✅ Так нужно — через Map
var a = new Map<string,string>()
a.set("prop", "hello world")

// ✅ Или через класс
class A {
  constructor(public prop: string) {}
}
var a = new A("hello world")
```

### Проверка null ограничена локальными переменными

В AssemblyScript проверка на null работает корректно только для локальных переменных, но не для свойств объектов :

```typescript
function doSomething(foo: Foo): void {
  // ❌ Не сработает — проверка свойства не гарантирует безопасность
  if (foo.something) {
    foo.something.length // может упасть
  }
}

function doSomething(foo: Foo): void {
  // ✅ Сработает — проверка локальной переменной гарантирует безопасность
  var something = foo.something
  if (something) {
    something.length // безопасно
  }
}
```

### Нет JSON-сериализации классов

На момент 2026 года в AssemblyScript нет встроенной поддержки сериализации и десериализации классов в JSON . Это создаёт сложности при обмене структурированными данными с хост-средой.

### Нет замыканий

В AssemblyScript нельзя создавать замыкания (closures) — функции, захватывающие переменные из внешней области видимости .

## Производительность vs нативные языки

Производительность AssemblyScript — сложная тема. Она сильно зависит от того, как написан код и какие возможности языка используются.

### Сравнение с C, C++ и Rust

Исследования показывают, что AssemblyScript может значительно отставать от компилируемых языков в вычислительно-интенсивных задачах. В одном из исследований алгоритм сортировки пузырьком на AssemblyScript выполнялся за **70–80 секунд**, тогда как C, C++ и Rust выполняли ту же задачу за **7–10 секунд** . Это различие в 7–10 раз связано с тем, что AssemblyScript компилируется в WASM не так эффективно, как Emscripten или Rust-компилятор .

Однако для задач, интенсивно взаимодействующих с WebAssembly-хостами (например, обработка HTTP-заголовков в прокси), разница может быть минимальной. Бенчмарк от Alibaba Cloud показывает, что AssemblyScript, C++, Go и Rust показывают **почти одинаковую задержку на запрос** — около 0.19–0.21 мс для типичной задачи работы с заголовками .

### Производительность vs JavaScript

AssemblyScript не делает существующий TypeScript-код «магически быстрее» только за счёт компиляции в WASM . Производительность зависит от того, какой код написан :

| Сценарий | Рекомендация |
|----------|--------------|
| Вычислительно-интенсивные алгоритмы | Используйте WebAssembly (AssemblyScript) |
| Интенсивное взаимодействие с DOM | Используйте JavaScript |
| Игры | Используйте WASM для CPU-интенсивных частей |
| Веб-сайты, блоги | JavaScript — ваш друг |

Ключевое наблюдение: если код активно использует управляемые объекты (`Map`, `String`, массивы), требующие управления памятью, выигрыш от WASM может быть минимальным или отсутствовать . Наибольший выигрыш дают функции, которые выполняют вычисления с числами и не пересекают границу между WASM и хостом .

### Проблемы с производительностью в 2026 году

Проблемы производительности AssemblyScript связаны с несколькими факторами:

1. **Отсутствие агрессивных оптимизаций компилятора.** В отличие от Emscripten (C/C++), который имеет десятилетия оптимизаций LLVM, AssemblyScript использует Binaryen и имеет меньше возможностей для оптимизации .

2. **Управляемая куча.** AssemblyScript использует управляемую память для объектов. Это создаёт накладные расходы на сборку мусора, особенно в циклах .

3. **Отсутствие встроенной многопоточности.** На момент 2026 года AssemblyScript не имеет полноценной поддержки многопоточности, что ограничивает его производительность на многоядерных системах .

## Когда выбирать AssemblyScript

AssemblyScript не является универсальным решением. Это инструмент, который хорошо подходит для определённых сценариев и плохо — для других.

### Хорошие сценарии для AssemblyScript

**1. Вычислительно-интенсивные задачи с числами.** Если задача состоит из математических вычислений и не требует сложных структур данных, AssemblyScript может дать хороший выигрыш по сравнению с JavaScript .

**2. Портирование существующего TypeScript-кода.** Если у вас есть TypeScript-код, написанный в строгом статическом стиле (без `any`, без динамических объектов), его можно портировать в AssemblyScript с минимальными изменениями .

**3. Плагины для API-шлюзов и прокси.** Бенчмарки показывают, что AssemblyScript сопоставим по производительности с C++, Rust и Go в задачах обработки запросов . Это делает его хорошим выбором для написания плагинов в экосистеме API-шлюзов, где разработчики привыкли к TypeScript.

**4. Игровая логика, эмуляторы, компиляторы.** AssemblyScript хорошо подходит для горячей игровой логики, эмуляторов и компиляторов, где требуется низкоуровневый контроль над памятью и вычислениями .

**5. Команды, знакомые с TypeScript.** Если команда разработчиков знакома с TypeScript и не хочет изучать Rust или C++, AssemblyScript предоставляет компромисс между производительностью и удобством .

### Плохие сценарии для AssemblyScript

**1. Интенсивное взаимодействие с DOM.** Каждое обращение к DOM требует пересечения границы WASM↔JS, что создаёт накладные расходы .

**2. Сложные структуры данных.** Отсутствие `any`, объединений типов и полноценной сериализации JSON делает работу со сложными данными неудобной .

**3. Приложения, требующие максимальной производительности.** Если важна каждая миллисекунда, Rust или C/C++ будут быстрее .

**4. Проекты, требующие WASI.** Поддержка WASI в AssemblyScript неопределённа из-за критики процесса стандартизации WASI со стороны команды AssemblyScript .

### Производительность как фактор выбора

Важно понимать: AssemblyScript не является заменой Rust или C++ для WebAssembly. Его производительность в вычислительно-интенсивных задачах может быть в **7–10 раз ниже**, чем у C/C++ . Однако для задач с интенсивным I/O или API-вызовами разница может быть минимальной .

---

AssemblyScript занимает уникальную нишу в экосистеме WebAssembly: это язык, который предоставляет синтаксис TypeScript, но с производительностью и контролем, приближающимися к «сырому» WASM. Он не подходит для всех задач, но для команд, знакомых с TypeScript и нуждающихся в небольшом ускорении вычислительных задач, он предоставляет компромиссный вариант. Однако для критичных по производительности приложений Rust или C++ остаются предпочтительным выбором .
