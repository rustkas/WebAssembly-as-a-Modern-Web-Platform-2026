# Глава 3. WASM vs JavaScript

JavaScript остаётся основным языком веб-платформы. WebAssembly не заменяет его, а дополняет. Чтобы понять, когда и зачем использовать каждую технологию, необходимо разобраться в их фундаментальных различиях: как они исполняются, как управляют памятью, как работают с типами и какую производительность дают в разных сценариях.

## Компилируемость против интерпретируемости

JavaScript — интерпретируемый язык с JIT-компиляцией. Исходный код не компилируется заранее. Браузер получает текст программы и на лету преобразует его в машинный код. Этот процесс состоит из нескольких этапов:

1. **Парсинг** — исходный код разбирается в абстрактное синтаксическое дерево (AST).
2. **Генерация байт-кода** — из AST генерируется промежуточное представление.
3. **JIT-компиляция** — часто выполняемый байт-код компилируется в машинный код для ускорения .

Парсинг и компиляция происходят в браузере пользователя, что добавляет время до начала выполнения. Для небольших скриптов это незаметно, но для больших приложений парсинг может занимать секунды.

WebAssembly работает иначе. WASM-модуль — это уже скомпилированный бинарный файл. Он не требует парсинга исходного кода. Браузер получает готовый байт-код, который можно сразу валидировать и компилировать в машинный код . Декодирование бинарного формата происходит значительно быстрее, чем парсинг эквивалентного JavaScript-кода.

Ключевое различие в том, как JIT-компиляция влияет на производительность в процессе выполнения. Исследования показывают, что JIT-оптимизации в Chrome значительно ускоряют JavaScript (в среднем в 38 раз), но практически не влияют на скорость WebAssembly . Это означает, что JavaScript становится быстрее по мере выполнения «горячих» участков кода, а WASM показывает стабильную производительность с самого начала.

В одном из экспериментов эта разница проявилась наглядно: реализация нейросетевого активатора на JavaScript использовала динамическую генерацию кода, который полностью JIT-компилировался в один оптимизированный блок машинного кода. WASM-реализация того же алгоритма использовала интерпретатор с циклом и функциями-диспетчерами, что сделало WASM примерно в 2.2 раза медленнее . Это показывает, что JIT-компиляция может давать JavaScript преимущество в сценариях с длительными повторяющимися вычислениями.

Однако в большинстве задач, где важна предсказуемость и низкая задержка старта, преимущество на стороне WASM. Бинарный формат загружается и компилируется быстрее, а производительность не зависит от «прогрева» JIT.

## Статическая против динамической типизации

JavaScript — язык с динамической типизацией. Тип переменной определяется во время выполнения. Одна и та же переменная может хранить число, строку или объект. Это удобно для разработки, но создаёт нагрузку на движок: перед каждой операцией он должен проверить тип операндов и при необходимости выполнить преобразование . Каждая инструкция JavaScript проходит через несколько проверок типов и преобразований, что замедляет выполнение .

Динамическая типизация также затрудняет компиляцию статически типизированных языков в JavaScript. С++ код, например, сложно эффективно транслировать в JavaScript, потому что модели типов принципиально разные .

WebAssembly использует статическую типизацию. В WASM-модуле типы всех значений известны заранее. Инструкции работают с конкретными типами: `i32`, `i64`, `f32`, `f64`. Это позволяет браузерному движку генерировать машинный код без дополнительных проверок типов во время выполнения. В результате каждая инструкция выполняется быстрее.

Стандарт WebAssembly 3.0, выпущенный в 2026 году, добавил поддержку сборщика мусора (GC) и ссылочных типов . Это открыло двери для языков с динамической типизацией, таких как Java, Scala, Kotlin, OCaml и Scheme, которые теперь могут компилироваться в WASM с сохранением своих семантик . Однако для языков вроде JavaScript прямой компиляции в WASM пока нет, и в ближайшем будущем ожидается лишь эволюционное улучшение существующих решений .

## Линейная память против управляемой кучи

JavaScript использует автоматическое управление памятью через сборщик мусора (GC). Память выделяется и освобождается автоматически. Это удобно и снижает риск утечек, но создаёт непредсказуемые паузы. Сборщик мусора может запуститься в любой момент, приостанавливая выполнение программы. Кроме того, управляемая куча накладывает ограничения на структуры данных и доступ к памяти.

Исследования показывают, что JavaScript значительно эффективнее использует память, чем WebAssembly . В одном из экспериментов потребление памяти JavaScript оставалось стабильным (около 884 КБ) независимо от размера входных данных. WebAssembly в тех же условиях потреблял от 36 МБ до 144 МБ . Причина в том, что WASM не поддерживает автоматическую сборку мусора для линейной памяти. Вместо этого при инстанцировании модуля выделяется большой непрерывный блок памяти, и если он заполняется, память расширяется, но не освобождается .

Это объясняет, почему приложения с интенсивным использованием памяти могут лучше работать на JavaScript, несмотря на более медленные вычисления. Например, в эксперименте с инференсом глубоких нейросетей WebAssembly обеспечивал более быстрое выполнение, но с существенно большим потреблением памяти, чем JavaScript .

Однако WebAssembly 3.0 вводит сборщик мусора для ссылочных типов . GC-объекты в браузере размещаются на той же куче, что и JavaScript-объекты, и ссылки между ними передаются без накладных расходов . Это позволяет языкам с управляемой памятью компилироваться в WASM, делегируя управление памятью браузерному сборщику, а не реализуя собственный GC внутри линейной памяти .

Традиционная линейная память остаётся основным механизмом для статически типизированных языков без сборщика мусора (C, C++, Rust). Разработчик управляет памятью через аллокаторы внутри выделенного буфера, и браузерный GC не видит, что происходит внутри этого буфера .

## Производительность: что и когда быстрее

Утверждение «WebAssembly всегда быстрее JavaScript» не соответствует действительности. Производительность сильно зависит от характера нагрузки и размера данных.

Исследование 30 бенчмарков на Chrome показало :

- **Для малых входных данных** WebAssembly быстрее JavaScript в среднем в 7.67–35 раз.
- **Для средних входных данных** более половины WASM-программ (56.7%) становятся медленнее JavaScript.
- **Для больших входных данных** количество случаев, где JavaScript обгоняет WASM, не увеличивается, но преимущество WASM существенно сокращается.

Причина в JIT-компиляции JavaScript. При обработке больших объёмов данных часто выполняемые циклы и функции получают агрессивную JIT-оптимизацию. JavaScript может догнать и даже обогнать WASM, который не получает такого же ускорения от JIT .

Однако это касается вычислительных задач. Для операций, связанных с DOM, WebAssembly не имеет прямого доступа и всегда вызывает JavaScript-функции для манипуляций с DOM. Накладные расходы на вызов могут свести на нет преимущества WASM. Поэтому WebAssembly не подходит для задач, интенсивно взаимодействующих с DOM.

В практике разработчиков наблюдается чёткая закономерность. Для задач, где выполняются короткие вызовы с малым объёмом данных, JavaScript оказывается быстрее из-за меньших накладных расходов на интероп. Для задач с длительными вычислениями и большим объёмом данных преимущество WASM становится заметным.

Физические симуляции и обработка графов — примеры, где WASM показывает преимущество . В симуляции частиц с N-тельным взаимодействием WASM значительно выигрывает на больших количествах объектов, особенно при использовании алгоритмов вроде Barnes-Hut, где WASM получает преимущество за счёт предсказуемой структуры памяти и отсутствия GC-накладных расходов .

## Когда использовать WASM, а когда JS

Выбор между WebAssembly и JavaScript определяется характером задачи .

### Сценарии для JavaScript

JavaScript остаётся предпочтительным выбором для:

- **UI и взаимодействия с DOM**. JavaScript имеет прямой доступ к DOM и API браузера. WASM вызывает JavaScript для любой DOM-операции, создавая накладные расходы.
- **Обработки событий**. Клики, ввод, загрузка — всё это обрабатывается через события. Модель событий JavaScript хорошо подходит для этих задач.
- **Небольших и средних проектов**. Для типичных веб-приложений JavaScript обеспечивает достаточную производительность при меньшей сложности разработки.
- **Задач с непредсказуемой нагрузкой**. JS эффективно использует память благодаря GC. Если приложение работает с большим количеством данных, но вычислений относительно немного, JS может быть предпочтительнее.

### Сценарии для WebAssembly

WebAssembly показывает преимущества в :

- **Вычислительно-интенсивных задачах**: обработка видео и аудио, криптография, симуляции, численные методы.
- **Играх и 3D-графике**: портирование игровых движков в веб.
- **Машинном обучении на клиенте**: инференс моделей в реальном времени.
- **Крупных кодовых базах**: перенос существующих C++/Rust-приложений в веб.
- **Задачах с большими объёмами данных и длительными вычислениями**, где JIT-преимущество JavaScript нивелируется.

### Гибридный подход

На практике многие приложения используют гибридный подход . JavaScript отвечает за UI, события и DOM, а WebAssembly выполняет «тяжёлую работу» — обработку данных, фильтрацию изображений, вычисления. Это позволяет использовать сильные стороны обеих технологий .

Вывод не в том, что одна технология лучше другой. WebAssembly и JavaScript решают разные задачи. Их совместное использование — современный подход к созданию высокопроизводительных веб-приложений.
