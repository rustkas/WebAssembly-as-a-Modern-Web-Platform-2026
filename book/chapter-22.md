# Глава 22. Управление памятью

Управление памятью в WebAssembly фундаментально отличается от JavaScript. Вместо управляемой кучи с автоматическим сборщиком мусора, WebAssembly использует **линейную память** — непрерывный массив байтов, доступ к которому осуществляется по адресу . Разработчик сам управляет выделением и освобождением памяти, что даёт предсказуемую производительность, но требует ручного контроля.

## WebAssembly.Memory

`WebAssembly.Memory` — это JavaScript-объект, представляющий линейную память WebAssembly-модуля . Он содержит сырые байты, к которым модуль обращается через инструкции загрузки и сохранения. JavaScript-код также может читать и писать в этот буфер через свойства `buffer`, что позволяет эффективно обмениваться данными с WASM-модулем без копирования.

Создание объекта памяти:

```javascript
const memory = new WebAssembly.Memory({
  initial: 1,   // начальный размер — 1 страница (64 КБ)
  maximum: 10,  // максимальный размер — 10 страниц (640 КБ)
});
```

При инстанцировании модуля память передаётся через импорты:

```javascript
const importObject = {
  env: { memory }
};

const { instance } = await WebAssembly.instantiateStreaming(
  fetch('module.wasm'),
  importObject
);
```

`WebAssembly.Memory` поддерживает как 32-битную, так и 64-битную адресацию. Для 64-битной памяти используется опция `addressType: "i64"`.

## Страницы памяти (64KB)

Память в WebAssembly измеряется в **страницах**. Одна страница равна 64 КБ (65,536 байт) . Этот размер фиксирован спецификацией и не может быть изменён.

Размер 64 КБ выбран как эффективный компромисс между гранулярностью выделения и накладными расходами на управление памятью. При создании `WebAssembly.Memory` разработчик указывает начальное и опциональное максимальное количество страниц. Если максимум не указан, память может расти неограниченно (до лимитов, установленных рантаймом и устройством).

## Рост памяти: grow()

Метод `grow()` увеличивает количество страниц памяти на указанное значение `delta` :

```javascript
const bytesPerPage = 64 * 1024;
console.log(memory.buffer.byteLength / bytesPerPage); // "1"
console.log(memory.grow(1));                          // "1" — возвращает прежний размер в страницах
console.log(memory.buffer.byteLength / bytesPerPage); // "2"
```

Возвращаемое значение — предыдущий размер памяти в страницах. Если новый размер превышает установленный максимум, выбрасывается исключение `RangeError` .

**Ключевая особенность**: каждый вызов `grow`, даже с `delta = 0`, **отделяет** существующий `ArrayBuffer` . После отделения:
- `byteLength` старого буфера становится равным нулю
- Доступ к данным через старый буфер становится невозможным
- Свойство `buffer` возвращает новый `ArrayBuffer` с обновлённой длиной

Это поведение важно учитывать при работе с типизированными массивами: после вызова `grow` необходимо заново создавать `Uint8Array` или другие представления буфера.

Для 64-битной памяти параметр `delta` и возвращаемое значение имеют тип `BigInt`.

## Утечки памяти в WASM

Хотя WebAssembly не имеет сборщика мусора для линейной памяти, утечки памяти в WASM-модулях возникают так же часто, как и в нативных C/C++-приложениях. Основные причины:

**1. Неосвобождённые выделения.** Если модуль выделяет память (например, через `malloc` или аллокатор в Rust) и не освобождает её, память остаётся занятой до завершения работы инстанса.

**2. Забытые указатели из-за `forget()`.** В Rust/WASM распространён паттерн использования `Closure::forget()` для предотвращения удаления замыканий, переданных в JavaScript . Каждый вызов `forget()` создаёт утечку памяти:

```rust
// Опасный паттерн — утечка памяти
let closure = Closure::once(move || {
    waker.wake();
});

window.set_timeout_with_callback(closure.as_ref().unchecked_ref(), interval_ms)?;
closure.forget(); // Утечка памяти!
```

В тестовых сценариях с частым опросом (каждые 50 мс) такая утечка может привести к значительному росту памяти за короткое время .

**3. Избыточное кэширование инстансов.** В серверных сценариях повторное использование одного WASM-инстанса для всех запросов может приводить к коррупции кучи и утечкам . Решение — использование пула инстансов с явным освобождением памяти после каждого запроса.

**4. Отсутствие освобождения на стороне хоста.** Если JavaScript выделяет память в WASM-модуле через экспортированную функцию `alloc`, но забывает вызвать соответствующую функцию `free`, данные остаются в линейной памяти бессрочно.

## Аллокация и освобождение

### Экспортируемые функции alloc/free

Стандартный паттерн управления памятью на границе JavaScript ↔ WASM — экспорт функций `alloc` и `free` из WASM-модуля . JavaScript вызывает `alloc` для получения буфера в линейной памяти, записывает данные, выполняет работу, а затем вызывает `free`.

```rust
// Rust-сторона
#[no_mangle]
pub extern "C" fn alloc(size: usize) -> *mut u8 {
    let mut buf = Vec::with_capacity(size);
    let ptr = buf.as_mut_ptr();
    std::mem::forget(buf);
    ptr
}

#[no_mangle]
pub unsafe extern "C" fn dealloc(ptr: *mut u8, size: usize) {
    if ptr.is_null() || size == 0 { return; }
    let align_units = size.div_ceil(8);
    drop(Vec::from_raw_parts(ptr.cast::<u64>(), 0, align_units));
}
```

```javascript
// JavaScript-сторона
const ptr = instance.exports.alloc(data.length);
const view = new Uint8Array(memory.buffer, ptr, data.length);
view.set(data);
instance.exports.process_data(ptr, data.length);
instance.exports.dealloc(ptr, data.length);
```

Этот подход даёт **нулевое копирование** при передаче данных: JavaScript записывает данные непосредственно в WASM-память.

### Блочные аллокаторы (Bump Allocators)

Для задач, требующих множества короткоживущих выделений (например, потоковая обработка кадров), используется **блочный (bump) аллокатор** — область памяти с простым указателем выделения и полным сбросом за один раз :

```rust
pub struct WasmBumpAllocator {
    buf: Vec<u8>,
    offset: usize,
}

impl WasmBumpAllocator {
    pub fn alloc(&mut self, size: usize, align: usize) -> Option<&mut [u8]> {
        let aligned_offset = (self.offset + align - 1) & !(align - 1);
        let end = aligned_offset.checked_add(size)?;
        if end > self.buf.len() { return None; }
        self.offset = end;
        Some(&mut self.buf[aligned_offset..end])
    }
    
    pub fn reset(&mut self) {
        self.offset = 0; // освобождает всё за O(1)
    }
}
```

Блочный аллокатор **не освобождает отдельные выделения** — вместо этого он сбрасывает весь буфер, когда он больше не нужен. Это эффективно для пайплайнов, обрабатывающих кадры или пакеты данных, где все временные данные имеют одинаковый жизненный цикл.

### Управление разделяемой памятью

Для разделяемой памяти (`SharedArrayBuffer`) в серверных рантаймах, таких как Wasmtime, существуют отдельные API для управления жизненным циклом :

- `wasmtime_sharedmemory_new` — создание разделяемой памяти
- `wasmtime_sharedmemory_clone` — поверхностное клонирование (увеличение счётчика ссылок)
- `wasmtime_sharedmemory_delete` — удаление (уменьшение счётчика ссылок)
- `wasmtime_sharedmemory_grow` — увеличение размера на `delta` страниц

Разделяемая память может использоваться несколькими инстансами и воркерами одновременно. При вызове `grow` на `SharedArrayBuffer` старый буфер **не отделяется** — вместо этого его длина не обновляется, а свойство `buffer` возвращает новый `SharedArrayBuffer`, указывающий на ту же память, но с большим диапазоном .

---

Управление памятью в WebAssembly — это ручной процесс, требующий понимания страниц, роста памяти и явных операций выделения/освобождения. Разработчик обязан следить за тем, чтобы каждый `alloc` сопровождался соответствующим `dealloc`, избегать утечек через `forget()` в долгоживущих приложениях и выбирать подходящие стратегии аллокации для своих сценариев использования.
